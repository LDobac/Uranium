# 학습 최적화 여지 검토: 데이터 공급(CPU)·학습 연산(GPU) (2026-11-16)

## 0. 배경과 예상

- 지시(사용자, 2026-11-16): CPU(데이터 로드)·GPU(학습 연산)에서 최적화할 수 있는 부분을 탐색·검토한다. 1차는 코드 수정 없이.
- 제약: 같은 수식의 빠른 구현만([032 모델 spec](../../spec/2026_10_15_22_24_032-model-architecture.md) R19), batch 내용·순서·데이터 위치 불변([041 모방학습 spec](../../spec/2026_10_15_22_24_041-imitation-learning.md) R13·R16).
- 이미 한 것: [pytorch_opt](../bench/2026_10_24_07_03_pytorch_opt.md)(10-24~28, BC 학습 중심), [flex_attention](../bench/2026_10_25_13_39_flex_attention.md). 여기서 채택·탈락한 항목은 다시 다루지 않는다.
- 예상(검토 전): BC 본학습은 10월에 짰으므로 여지가 작고, 그 뒤에 생긴 경로(모델 2 모듈, 섞기 run, RL 학습기)에 남아 있을 것.
- 방법: 코드 읽기 + 기존 학습 로그 집계(1~3절), 이어서 실측(4절).

- 파일당 디코드: 빈 캐시로 `uranium-train split-stats`를 돌려 4스레드 벽시계 1.9초/파일(`community` 43개 82.9초, `scr_ladder` 106개 203.9초). 0판 파일 수 × 1.9초 = 2,700~3,100초로 대기 합의 1.4~1.8배 → 자릿수가 맞는다. 공급 경로의 단일 스레드 파일당 시간과 건너뛴 뒤 실제 대기 감소는 구현 뒤 측정.

## 5. D1·D2 구현 계획

근거: [041 모방학습 spec](../../spec/2026_10_15_22_24_041-imitation-learning.md) R13(2026-11-16 개정). 문구 확인 뒤 착수.

| 단위 | 내용 | 파일 | 검증 |
|---|---|---|---|
| U1 (D2) | 스캔 캐시를 파일 단위 항목으로(파일 키 + 내용 지문), 캐시 버전 올림, 없는 파일만 스캔 | `crates/uranium-data/src/data/scan.rs`, `tests/bc.rs` 캐시 테스트 | 파일 하나 추가 뒤 그 파일만 스캔, 옛 캐시는 무시하고 다시 만듦 |
| U2 (D1) | 시작 스캔 결과로 선택·subsample 뒤 남는 게임이 0인 파일 집합을 계산해 `ShardSource::only_files`에 연결(학습 공급 경로 전부: `bc_run`, `uranium._core` 공급 생성) | `crates/uranium-data/src/bc.rs`·`bc_run.rs`·`data/source.rs`, `crates/uranium-py/src/lib.rs` | 켜기 전후 게임 순서·batch digest(`feed-digest`)·데이터 위치 일치, 재개(`seek`) 뒤 일치 |
| U3 | 실측 | — | `config/bc_m2_teacher_t1.toml` 조합으로 CUDA 100 update의 `wait_secs`·시작 스캔 시간 전후 비교 |

- 순서: U1 → U2(같은 crate, 한 worktree) → 리뷰 → U3.
- 시간을 정하는 것: U1·U2는 에이전트(시간 단위), U3는 GPU 약 5분 + 첫 스캔.
- 데이터 위치: 건너뛰어도 게임이 빈 상태의 위치는 `next_file` 기준이고 `next_game` 한 번 안에서 다음 비지 않은 파일까지 가므로 호출 사이 상태가 같다(코드 읽기, U2 테스트로 확인).
- 하지 않는 것: D3(파일 미리 읽기)는 U3 결과에서 대기가 남을 때 다시 판단.
