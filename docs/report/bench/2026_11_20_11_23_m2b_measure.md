### 4. 추론 서버 메모리

방법은 2.5 GiB 행의 근거와 같다([opt_review] 7.6절, [pytorch_opt] 2.25절의 측정 스크립트): torch·장치 준비 뒤를 기준으로, 추론 서버 생성·워밍업 뒤 배치 1, 2, 3, 4, 6, 8, 12, 16, 24, 32 × 엔티티 64~N(64씩)을 모두 거친 뒤 MemAvailable 감소. 3회 반복.

| 범위 | 기본 할당자 | `expandable_segments` 켬 | 모델 2(같은 방법) |
|---|---|---|---|
| 엔티티 64~256 | **3.18~3.20 GiB** | 2.90~2.93 GiB | 2.25 GiB |
| 엔티티 64~512 | 4.59~4.62 GiB | 3.60~3.65 GiB | 2.87 GiB |
| 배치 6 이하 × 64~512(3판 실게임 범위) | 3.14~3.19 GiB | 3.08~3.13 GiB | 2.38 GiB |

- 기준선 자체(torch·장치 준비)는 RSS 0.46 GiB + GPU 0.20 GiB다. 추론만 하는 별도 프로세스면 위 값에 약 0.7 GiB를 더한다.

### 5. 발견: 캐시 할당자 조각화

| 측정(별도 프로세스, torch 불러오기 전 기준 MemAvailable 감소) | 64~256 | 64~512 |
|---|---|---|
| 배치 1~32 정수 전부, 엔티티 바깥 루프 | 6.0 GiB | 8.2 GiB |
| 같은 순서, 그래프 끔 | 5.3 GiB | – |
| 같은 순서, 배치 8까지 | 2.6 GiB | 3.4 GiB |
| 같은 순서, `expandable_segments` 켬 | 2.8 GiB | 3.7 GiB |

- 원인: torch 캐시 할당자. 같은 측정에서 torch 최대 할당은 1.4 / 2.1 GiB인데 예약(reserved)은 4.9 / 5.9 GiB였다. 그래프를 꺼도 비슷해 그래프 탓이 아니고, 배치 5~32의 그래프 없는 큰 배치가 크기마다 다른 블록을 남긴다.
- 같은 모양 집합이라도 지나는 순서에 따라 4절 값(3.2 / 4.6)과 이 값(6.0 / 8.2)처럼 갈린다. 실게임 배치 순서에서 어느 쪽에 가까운지는 재지 않았다.
- `expandable_segments`는 순서와 거의 무관하게 2.8~3.7 GiB로 묶는다. 지연은 3절처럼 같거나 조금 빠르다.

### 7. 한계·주의

- **`URANIUM_BC_PAD_ENTITIES` 주의:** Linux ROCm 호스트 학습 기본값 `URANIUM_BC_PAD_ENTITIES=32`(`python/uranium/device.py` 학습 기본값)가 설정의 `pad_entities`를 덮어쓴다. 설정 사본에 `pad_entities = 512`만 두면 최악 모양이 아니다(첫 시도는 엔티티 32 단위로 돌아 16.2초·GPU 5.9 GiB, 버림, 원자료 `first/pad32_personal/`). 최악 모양은 환경변수 `URANIUM_BC_PAD_ENTITIES=512`로 다시 쟀다.
- 추론 측정은 합성 입력·무작위 초기화 모델이다. `--served`·스크립트는 서버 전용 stream(`URANIUM_INFER_STREAM`)을 쓰지 않아 실게임 지연과 조금 다를 수 있다. 실게임 지연·메모리는 재지 않았다.
- `bench bc`의 16 update 동안 학습 손실이 10 → 20으로 올랐다(최악 모양·실데이터 모두). 벤치 짧은 구간이라 원인은 보지 않았다.
- 재계산 끔은 둘째 update 중 메모리 바닥에서 측정 보호 장치(MemAvailable 0.7 GiB 미만이면 종료)가 끊었다. 최대값은 하한이다.
- 최악 모양 6 update, 설정마다 1회.
