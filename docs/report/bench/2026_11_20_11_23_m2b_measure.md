### 7. 한계·주의

- **`URANIUM_BC_PAD_ENTITIES` 주의:** Linux ROCm 호스트 학습 기본값 `URANIUM_BC_PAD_ENTITIES=32`(`python/uranium/device.py` 학습 기본값)가 설정의 `pad_entities`를 덮어쓴다. 설정 사본에 `pad_entities = 512`만 두면 최악 모양이 아니다(첫 시도는 엔티티 32 단위로 돌아 16.2초·GPU 5.9 GiB, 버림, 원자료 `first/pad32_personal/`). 최악 모양은 환경변수 `URANIUM_BC_PAD_ENTITIES=512`로 다시 쟀다.

- `bench bc`의 16 update 동안 학습 손실이 10 → 20으로 올랐다(최악 모양·실데이터 모두). 벤치 짧은 구간이라 원인은 보지 않았다.
- 재계산 끔은 둘째 update 중 메모리 바닥에서 측정 보호 장치(MemAvailable 0.7 GiB 미만이면 종료)가 끊었다. 최대값은 하한이다.
- 최악 모양 6 update, 설정마다 1회.

- 원래 줄기 실제 학습 로그는 처음부터 끝까지 평평하다(10구간 중앙값 1.44~1.45, 처음 2~101 대 2,000~끝 비 0.95~1.00: `m2-s1`·`m2-s1e2`·`m2-s2e2`·`m2-teacher-t2`·`m2-gn-t1e2`). 지금 크기는 엔티티 인코더 몫이 작아서로 본다(추정). 그래서 이 비(약 1.0)는 B에 쓰지 않는다.
- 정상 상태 어림: 모양이 510까지 다 나온 update 50~100 구간의 `reduce-overhead` 중앙값 3.62초를 쓴다(이 구간 넘침 영향은 작아 보임, `default`가 update 1~9에서 7% 느린 것과 상쇄로 봄, 추정). 혼합은 같은 구간 비(update 21~30, 2.79/3.23 = 0.86)로 3.1초. 상한은 최악 모양 5.67초(4절).
- 재구성은 update 700 근처까지 돌다가 이 PC 메모리 부족(표본 끝-끝 실행과 동시)으로 도구가 끊었다. update 564에 512가 처음 나왔고, update 300·600 구간 최대는 382·446이었다(정상 상태 분포를 끝까지 세지는 못함).

### 5. 입력 모양별 GPU 메모리 증가

| 새 모양(엔티티 열, 처음 나온 update) | `reduce-overhead`(재계산 끔) GPU 전용 | `default`(고른 설정) GPU 전용 |
|---|---|---|
| 126·190 (0) | 7.1 GiB | 6.8 |
| 192 (8)·254 (9) | 9.8~11.0 | 8.6~10.6 |
| 256 (12)·318 (14) | 11.7~12.1 | 10.6 |
| 382 (22)·320 (27) | 13.3 | 11.6 |
| 446 (33) | 14.4~14.6 | – (30 update 안에 안 나옴) |
| 510 (48)·384 (49) | 15.7(꽉 참) + 공유 2.5~2.9 | 최악 모양 실행 11.66 |

- 2초 표본과 update 끝 시각을 맞춘 값이라 ±1 update 오차가 있다.
- 나올 수 있는 모양: 패딩 64 단위 × 1~8, 추가 토큰 2개를 자른 것과 안 자른 것(62~512) 최대 16종. 재구성 700 update 안에서 13종(126, 190, 192, 254, 256, 318, 320, 382, 384, 446, 448, 510, 512).
- `reduce-overhead`: 새 모양마다 약 0.4~1.5 GiB씩 늘어 11종에서 넘쳤다. 모양마다 CUDA graph를 따로 기록한다는 torch 경고("9 distinct sizes")는 확인, 메모리 풀이 모양마다 쌓인다는 것은 이 증가 모양에서 본 추정이다. 16종이면 더 넘친다.
- `default`: CUDA graph가 없어 가장 큰 모양 하나로 정해진다고 본다(추정). 382에서 이미 11.63, 512 전용 실행 11.66이라 예측값 약 11.7 GiB. 단 캐시 할당자 조각화(Linux ROCm 호스트 5절)로 긴 run에서 더 클 수 있다. 줄이는 설정 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`는 아래 추가 측정에서 속도 그대로·GPU 전용 11.63 → 9.44 GiB(표본 학습 9.4~10.4 GiB).
- 추가 측정(사람 30 update, 그룹 2 + 재계산 끔 + `default`):

  | 할당자 | 중앙값(p95) | torch 최대 할당 | GPU 전용 최대 | 공유 | RSS | total 손실 update 0~3 |
  |---|---|---|---|---|---|---|
  | 기본 | 2.81초(3.37) | 8.83 GiB | 11.63 GiB | 0.67 | 8.2 | 9.9672·11.3736·12.4508·13.0682 |
  | `expandable_segments:True` | 2.805초(3.38) | 8.80 GiB | **9.44 GiB** | 0.65 | 7.9 | 9.9672·11.3738·12.4509·13.0687 |

  - 손실 차이 update 0~7에서 1e-4 이하(bf16 수준). 전용 추이 1.1 → 2.2 → 5.4 → 6.4 → 7.5 → 8.4 → 9.4 GiB로 계단식이지만 폭이 작다. 속도 손해 없이 할당자가 쥔 몫이 필요량에 가까워진다.
- 모양별 풀이 없는 다른 기존 모드: `URANIUM_COMPILE=max-autotune-no-cudagraphs`(`python/uranium/device.py` `COMPILE_MODES`). `default`보다 낫다는 기록이 없어 재지 않았다.

### 8. 발견

| 항목 | 내용 |
|---|---|
| 재계산 + `reduce-overhead` | 재계산 8: 첫 update 손실 전부 non-finite. 재계산 16: 45분 안에 컴파일 못 끝냄(RAM 15.4 GiB). 재계산 8 eager는 유한 → 재계산(`net.py` `entity_chunked`, `torch.utils.checkpoint`)과 `torch.compile` `reduce-overhead`의 조합 문제(확인). 그 안에서 CUDA graph 버퍼 재사용과 compile된 checkpoint 재계산 + 직접 작성 커널(`uranium::attn_bias_*` custom op) 중 어느 쪽인지는 미확인. `default` + 재계산은 안 잼 |
| [041]-R3 non-finite 처리 | `bc/trainer.py` `skip_update`: optimizer step만 건너뛰고 non-finite 코어 상태를 리셋한 뒤 계속 돈다. 연속 횟수 제한·중단 없음(stderr 한 줄씩). 본 줄기에서 조용히 헛돌 수 있다 |
| `bench/realbc.py` 결함 | 54행 `out['total']:.5f`가 non-finite(None) 손실에서 `TypeError`로 벤치를 끝낸다 |
| `URANIUM_BC_PAD_ENTITIES` | 설정 `pad_entities`를 덮어쓴다(Linux ROCm 호스트 7절). 최악 모양은 환경변수로 명시해야 한다 |
| 초반 손실 | 벤치 학습률은 실제 학습과 같다(`_core.lr_at`, warmup 2000, update 0 1.5e-7 ~ 100 1.515e-5, `m2-s1` 로그 `lr`과 일치). data seed가 같아 batch 순서도 같다(`target_loc` update 10 4.78 / `m2-s1` 4.73, 50 5.15/5.12, 100 5.19/5.21). total 10 update 평균 B 14.8 → 20.2(20~30) → 15.8(100), `m2-s1` 13.6 → 20.9 → 17.5. 10 → 20 상승은 원래 모델에도 같아 발산 신호가 아니다 |

### 9. 한계

- 속도는 30 update(고른 설정)·100 update(첫 실행)이고 설정마다 1회다. 정상 상태 값은 다른 compile 모드 구간에서 빌린 어림이다.
- 지금 크기 기준은 같은 날 재측정이 아니다(2절).
- 추론은 무작위 초기화·합성 입력이고 `--served`는 서버 전용 stream(`URANIUM_INFER_STREAM`)을 쓰지 않는다. 엔티티 64~256 단독 범위는 재지 않았다.
- GPU 메모리는 어댑터 전체 카운터(다른 프로그램 몫 포함)다. 프로세스별 값이 아니다.
- 고른 설정의 GPU 전용 추이는 평평해지지 않고 새 모양이 나올 때마다 계단식으로 는다(사람 30 update 3.9 → 6.7 → 8.6 → 10.6 → 11.6 GiB, 혼합 5.5 → 8.3 → 9.8 → 10.9 → 12.6 GiB). 최악 모양 실행만 11.66에서 평평했다.
