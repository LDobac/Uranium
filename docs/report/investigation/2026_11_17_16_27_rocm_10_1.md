# Linux ROCm 호스트 ROCm 10.1 전환 조사 (2026-11-17)

- 배경: 첫째 Linux ROCm 호스트에서 12:16 전체 패키지 업그레이드로 ROCm 7.2.4 → 10.1. 프로젝트 실행 환경에서 torch import 실패(`libhipblas.so.3: undefined symbol: rocblas_set_batch_alpha_stride`). 둘째 호스트는 7.2.4 그대로.
- 사용자 지시(2026-11-17): 최신을 쓸 수 있으면 코드 수정·둘째 호스트도 올림, 못 쓰면 되돌림.
- 예상: 그 GPU용 rocBLAS만 10.1 소스로 다시 빌드하면 된다.
- 결론: **쓸 수 있다.** rocBLAS 재빌드 + MIOpen 버전 검사 건너뛰기 설정으로, 시험한 범위(장치 테스트·벤치 스위트·BC 벤치 12 update)에서 결과·속도·메모리가 7.2.4와 같다. torch 재빌드는 필수 아님(4절).
- 산출물: 첫째 호스트 `local/work/rocm_update/`(로그·벤치 출력), `local/scripts/rocm101_*.sh`·`rocm724_rollback_sudo.sh`·`rocm_hold_sudo.sh`.

## 1. 원인

| 항목 | 내용 |
|---|---|
| 무엇이 올렸나 | AUR 도우미가 실행한 전체 업그레이드(`pacman -Syu`) 한 번. 새로 설치한 패키지(sway, sunshine 등)는 ROCm에 의존하지 않음. ROCm 밖에서 ROCm을 요구하는 패키지 없음 |
| 바뀐 것 | ROCm 패키지 34개 7.2.4 → 10.1, 새 패키지 3개(`rocm-llvm-libs`, `rocm-openmp`, `amdsmi`). HIP 런타임 7.2 → 7.16, MIOpen 3.5.1 → 3.6.1. 커널(`linux-lts`, 고정)·패치한 amdgpu 모듈·부팅 인자·SDMA 펌웨어 교체는 그대로 |
| import 실패 이유 | 홈의 rocBLAS는 7.2.4 소스 빌드라 새 hipBLAS가 찾는 기호가 없음 |
| 시스템 rocBLAS만 쓰면(`LD_LIBRARY_PATH` 없이) | import·단순 연산은 되지만 **첫 행렬곱에서 중단**: `rocBLAS error: Cannot read …/TensileLibrary.dat … for GPU arch : gfx1013`(15:36 시험). 10.1 패키지에도 이 GPU 커널이 없음(7.2.4 때와 같음, [torch_vs_burn](../bench/2026_10_23_18_30_torch_vs_burn.md)) |

## 3. 시험 (첫째 호스트, 단독)

비교 대상 7.2.4는 패키지 캐시를 홈에 풀어 `LD_LIBRARY_PATH`로 올린 것(시스템 변경 없음). 오전 값(10.40초, 같은 손실)을 재현한다.

| 시험 | 7.2.4 | 10.1 |
|---|---|---|
| 장치 테스트 `pytest tests/python -m gpu` | 19 통과·9 건너뜀 (4회 중 1회 1 실패) | 19 통과·9 건너뜀 (5회 중 3회 1 실패) |
| 직접 쓴 커널(HIP, 새 컴파일러로 다시 빌드)·기준 구현 비교 | 통과 | 통과. 7.2.4 때 빌드한 캐시도 통과 |
| `bench suite --suite kernels,model,infer` 40개 | 실패 없음 | 실패 없음. CPU 대비 오차는 같거나 3% 이내 차이(attention 2개), 시간 비 0.93~1.06(작은 f32 행렬곱 2개는 같은 버전에서도 실행마다 흔들려 제외) |
| BC 벤치([opt_review](../review/2026_11_16_21_25_opt_review.md) 7.16절과 같은 명령) update 중앙값(p95) | 10.59(11.39), 10.87(11.53)초 | 10.37(11.28), 10.30(10.80)초 |
| BC 벤치 update별 손실 13개 | 오전 값과 같음 | 12개 같음, 마지막 17.58355 대 17.58356 |
| torch 최대 GPU 메모리 | 2.91 GiB | 2.91 GiB |
| 프로세스 RSS 최대 / GTT 최대 (실행 2회) | 3.36·3.62 / 4.59 GiB | 3.58·3.50 / 4.61 GiB |

- `-m gpu` 시험의 변수: pytest는 호스트 `.env`를 읽지 않으므로(`tests/python/conftest.py`) 10.1 실행은 셸에서 `PYTORCH_SKIP_CUDNN_COMPATIBILITY_CHECK=1`을 export했다. 없이 돌린 첫 실행은 `test_gpu_matches_cpu_032_ac1_ac8[tiny-lstm]`에서 버전 검사 오류로 멈춤(`gpu_tests_nocompat.log`). 7.2.4 실행은 변수 없음.
- 실패 1건은 `test_update_on_the_device_matches_the_reference_032_r19[bf16]`의 **update 통계 비교**(`close_stats`, 둘째 update 손실 상대차 약 4e-3, 허용 1e-3)이고, 그 뒤의 가중치 비교까지는 가지 않았다. 근거(`local/work/rocm_update/`): 10.1 `gpu_tests_skipcheck.log`·`gpu_tests_101_run2.log`·`rep_101_1.log`, 7.2.4 `rep_724_2.log`. 두 버전 모두 가끔 실패(횟수가 적어 빈도 차이는 판단 못 함), 단독 실행은 통과. ROCm은 f32로 학습하므로([032-R8](../../spec/2026_10_15_22_24_032-model-architecture.md)) 쓰는 경로가 아님. 같은 테스트 f32의 가끔 실패는 [opt_review](../review/2026_11_16_21_25_opt_review.md) 7.15절에 기록됨.
- MIOpen find-db는 버전별이라 10.1에서 새로 쌓인다: 첫 BC 벤치 update 47·40·22초 뒤 정상.

## 4. 필요한 것과 선택

| 항목 | 내용 |
|---|---|
| rocBLAS | 10.1 소스 빌드를 홈의 새 폴더에 두고 기존 경로를 그쪽 링크로(7.2.4 빌드는 보관). sudo 불필요 |
| MIOpen 버전 검사 | torch가 MIOpen 3.5.1로 빌드돼 LSTM 초기화에서 `cuDNN version incompatibility` 오류 → 호스트 `.env`에 `PYTORCH_SKIP_CUDNN_COMPATIBILITY_CHECK=1` |
| torch 재빌드 | 필수 아님. 하면 위 설정이 필요 없어짐. 비용: 호스트당 약 1시간 50분(10-23 빌드 기록), 또는 한 대에서 빌드해 wheel 복사. 새 HIP 헤더로 빌드가 되는지는 시험 안 함. 기본안(미확정): 지금은 안 함 |
| 저장소 | [commands.md](../../guide/commands.md) 설치 절, `.env.example` 키 설명. 코드·spec 변경 없음(3절 시험 범위에서 코드 수정 없이 통과, 버전·절차는 리포트에 둠, [060](../../spec/2026_10_15_22_24_060-infra.md) 환경 표) |

## 5. 둘째 호스트 절차 (측정이 끝난 뒤, 미실행)

1. 사용자: `local/scripts/rocm101_upgrade_sudo.sh`(전체 업그레이드, sudo). 스크립트는 첫째 호스트에 있으므로 먼저 복사.
2. `local/scripts/rocm101_build_rocblas.sh`(12분) 또는 첫째 호스트의 빌드 결과 복사.
3. `local/scripts/rocm101_switch.sh`(경로 링크, `.env` 설정, 행렬곱 확인).
4. 확인: `-m gpu` 테스트, BC 벤치 한 번(첫 실행은 find-db 때문에 느림).
- 그때 저장소가 10.1보다 새 버전을 주면 두 호스트 버전이 달라진다 → 첫째 호스트도 같이 올리고 rocBLAS를 그 버전으로 다시 빌드하거나, 올리기 전에 `rocm_hold_sudo.sh`로 버전을 묶는다(사용자 결정).

## 6. 과거 측정값과의 비교 가능성

- 고정 조건이 ROCm f32인 측정(`val500` 등, [measurement_protocol](../../guide/measurement_protocol.md)): 3절에서 연산별 오차가 같고 12 update 학습 손실이 1e-5 안에서 같다. 문서에 이미 적힌 실행 간 흔들림(p(행동) 6e-6)과 같은 크기라 과거 값과 비교 가능하다고 본다.
- 직접 확인은 안 함: 같은 체크포인트의 `val500`을 두 버전에서 다시 재는 것. 기본안(미확정): 둘째 호스트를 올린 뒤 한 번 재서 기록.
- 두 호스트 버전이 다른 동안, 기본안(미확정): 한 측정 묶음은 한 버전에서.

## 7. 되돌리기 (대안, 미실행)

- 되돌릴 7.2.4 패키지가 패키지 캐시에 모두 있음. `local/scripts/rocm724_rollback_sudo.sh`(새 패키지 3개 중 `rocm-llvm-libs`·`rocm-openmp` 2개는 제거, `amdsmi`는 캐시의 7.2.4로 바꿈, 나머지는 캐시에서 설치. 시험 안 함). 되돌려도 깨지는 외부 의존 없음.
- 다시 올라가지 않게: `local/scripts/rocm_hold_sudo.sh`(설치된 ROCm 패키지를 `IgnorePkg`에 추가).
- sudo 없이: 3절의 방법(캐시를 홈에 풀어 `LD_LIBRARY_PATH`)으로 7.2.4 스택을 그대로 쓸 수 있음(약 22 GB).

## 8. 남은 위험·확인 못 한 것

- 장시간 학습(24시간), RL learner, 실게임 추론 서버는 10.1에서 돌려 보지 않음. 드문 GPU 멈춤 빈도 변화는 모름.
- 재부팅 뒤 동작(오늘 initramfs가 다시 만들어짐, 모듈·펌웨어 포함은 확인).
- torch(HIP 7.2 헤더로 빌드)와 HIP 7.16·MIOpen 3.6.1 런타임의 조합은 시험한 범위에서만 확인.
- 둘째 호스트의 실제 업그레이드.
- 모델 2 최악 모양 메모리 벤치([060-AC7](../../spec/2026_10_15_22_24_060-infra.md))는 10.1에서 돌리지 않음. 메모리는 BC 벤치(3절)만 확인.
- 장치 테스트 bf16 통계 비교의 실패 빈도(7.2.4 4회 중 1, 10.1 5회 중 3)가 버전 차이인지는 횟수가 적어 판단 못 함.
- 시험 안 한 스크립트 2개: `rocm101_upgrade_sudo.sh`, `rocm724_rollback_sudo.sh`(`rocm_hold_sudo.sh`도 실행 안 함).
