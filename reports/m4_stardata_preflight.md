# STARDATA 전체 build 전 표본 검증 (2026-10-17)

전체 build(약 36시간)를 다시 하지 않도록, shard 내용(관측·레이블·GameInfo)에 영향을 주는 문제를 표본으로 먼저 찾았다.

## 표본
- STARDATA 원본에서 `--parts 300 --part 0`(인덱스 % 300 == 0)으로 고르게 219개 → written 103 · filtered 119 · desync 2 · unplayable 1. 로컬 jobs 12로 약 7분.
- shard 6개(약 111MB), 103게임, 판단 스텝 232,413개. 매치업 TvP 48 · TvZ 43 · TvT 12, 맵 패밀리 투혼 17 · 서킷브레이커 2 · 기타 84.
- 전체 규모로 환산하면 local jobs 12 기준 약 35시간(기존 추정과 같음).

## 확인한 것
| 항목 | 결과 |
|---|---|
| schema 2 / `GameInfo` (AMB-040-6) | 103게임 모두 일관(맵 크기·지형 높이·시작 위치·self_player = perspective) |
| 레이블 커버리지 (031-AC3) | 98.91% (목표 ≥ 95%) |
| 액션 분포 (034) | 100개 중 90개 등장. 미등장 10개는 드문 기술(Lockdown, Restoration, Optical Flare, 관련 연구·업그레이드)과 `Load_Unit`(태우기는 대부분 우클릭 = `Smart_Unit`) |
| BC 끝까지 실행 (041) | CUDA, 레인 2, 600 업데이트 완주·체크포인트 저장. action loss 2.65 → 약 1.2–1.5, delay 2.74 → 약 2.1 |

| 애드온 발자국 위치를 비대칭 `dimensions`로 계산 (034-R3) | 머신샵이 한 칸 어긋나 시즈탱크·드랍십 생산 마스크가 100% 닫힘 | `top_left`를 BWAPI 규칙(`tile*32 + tile_size*16`)으로 | 아니요 (feature 코드) |

무효 레이블 비율: 17.62% → **6.57%**. 남은 무효:
- `type_mask`(7,154건): 미네랄 부족·인구수 막힘 상태의 연타 등 게임에서도 실패하는 명령. 031-R4대로 weight 0.
- `select_cap`(7,276건): 일부만 명령 자격이 있는 혼합 선택(메딕 섞인 스팀·어택땅, 서플라이 디팟 섞인 랠리 등). 학습 시점 판정 정책이라 shard와 무관.

## 결정 (본 build 전, 2026-10-17 사용자 확정)
- 대상 지정 명령(0x15) 중 034 액션에 매핑되지 않았던 order: `HealMove`(177, 메딕 어택땅) 1,666건, `Guard`(2) 129건, `TowerGuard`/`TowerAttack` 6건.
- `HealMove` 위치 대상은 `Attack_Pos`, 유닛 대상은 `Heal_Unit`으로 변환한다. 나머지는 `Unknown`으로 둔다(040-R11 반영).

## 본 build와 무관한 발견 (M5)
- 기본 BC 설정(레인 32 × T64)은 16GB GPU에서 메모리 부족. 실제 게임은 엔티티가 상한 512에 자주 닿아 엔티티 attention(N²)이 행마다 수 MB를 쓴다. 레인 8도 부족, 레인 2는 동작. f16·배치·체크포인팅 조정이 필요하다(032-AC3 측정은 N=256 기준이었다). → 2026-10-17 해결: `micro_lanes` gradient 누적(`reports/m5_bc_memory.md`).
- `uranium-replay build`의 재개 기능은 records 폴더에서 이름이 `<src>`로 시작하는 모든 `.jsonl`을 읽는다. 표본 records는 별도 하위 폴더에 둬야 본 build가 표본 리플레이를 건너뛰지 않는다.

## 혼합 선택·선택 추적 (2026-10-17, AMB-041-1, 사용자 위임으로 Claude 결정)

같은 1/300 표본(219개)을 고치기 전후로 다시 build하고 `label-check`로 비교했다. 판단 기준은 게임 엔진(OpenBW `actions.h`·`bwgame.h`)이 명령을 유닛마다 어떻게 처리하는지와, OpenBW 브리지가 거치는 BWAPI 4.2 `can*` 검사다.

| 원인 (수정 전 `select_cap` 실패) | 건수 | 엔진 동작 | 조치 |
|---|---|---|---|
| 어택땅에 섞인 메딕·베슬·드랍십 | 3,184 | AttackMove는 이동 가능한 모든 유닛이 받는다. 무기가 없으면 이동, 메딕은 HealMove | `Attack_Pos` 자격 `can_move`. BWAPI가 거부하는 비무장 유닛은 shim이 `move`로 보낸다 |
| 떠 있는 건물 우클릭이 `SetRally`로 바뀜 (배럭·CC·팩토리·엔베 등) | 약 2,300 | 떠 있는 건물의 우클릭은 이동 | 레이블러: 착지한 건물만 `SetRally_*`(040-R11) |
| 건설 중 생산 건물 랠리 | (위에 포함) | 게임·BWAPI 모두 허용 | `can_rally`에서 완성 조건 제거 |
| 우클릭·어택땅에 섞인 시즈모드 탱크, 이미 탱크 모드인 탱크, 체력 10 이하 마린 스팀, 마인 없는 벌처 | 수천 | 해당 유닛만 건너뜀 | 041-R11: 자격 없는 유닛을 레이블에서 빼고, 남는 유닛이 없을 때만 무효 |
| 시즈모드 탱크로 적 우클릭(점사) | 약 500 | 제자리 공격(`right_click_action` 3) | `Smart_Unit` 자격 `can_right_click_unit`(이동 가능 ∨ 시즈모드 탱크) |
| 탑승한 유닛이 선택에 남음, 다중 선택에 건물 섞임 | 수백 | 탑승은 즉시 선택 해제, 건물은 다중 선택 불가 | 레이블러 선택 추적을 게임 규칙과 일치(040-R3) |

선택 추적 수정은 shard 내용(`selected`)을 바꾸므로 shard schema를 3으로 올렸다. 나머지는 학습 시점 판정이다(feature schema 3).

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| 게임 / 레이블 | 103 / 233,798 | 102 / 226,289 |
| 무효 레이블 | 16,937 (7.24%) | **8,104 (3.58%)** |
| `select_cap` 무효 | 8,941 | 493 |
| `type_mask` 무효 | 7,154 | 7,044 |

- 남은 `select_cap` 무효는 게임에서도 효과가 없는 명령이다(마인 없는 벌처 311, 생산·연구 중인 건물 띄우기, 생산이 없는데 취소, 컴샛 우클릭, 에너지 부족 스킬).
- 게임 수 차이(103 → 102)는 디싱크 판정 1건(2 → 3)이다. 레이블러는 디싱크 판정에 쓰이지 않으므로 기존에 기록된 드문 재생 비결정성으로 본다.
- shim의 비무장 유닛 `move` 대체는 빌드만 확인했고, OpenBW 게임 안에서는 아직 실행해 보지 않았다(031-AC1 시나리오와 함께 확인).

`label-check`의 `type_mask_prereq`(실패한 선행 조건과, 바로 앞 스텝에서도 같았는지 old/new)와 대상 실패 분류로 확인했다.

| 사유 | 건수 | 내용 | 판단 |
|---|---|---|---|
| `type_mask` 자원·인구수 부족 | 7,044 (87%) | SCV 3,479, 시즈탱크 718, 마린 466, 벌처 457, 연구·업그레이드. 대부분 앞 스텝에서도 이미 부족(old) | 자원이 모이기 전 미리 누르기·연타. 게임도 거부하므로 무효가 맞다 |

## 도구
- `uranium-replay shard-stats <dir>`: 액션 분포, delay bucket, 인자 사용률, GameInfo 검사.
- `uranium-train label-check --shards <dir>`: 마스크에 걸리는 레이블을 액션·사유별로 집계.
- build records의 `coverage.unknown_orders`: 매핑되지 않은 0x15 order id별 건수.
