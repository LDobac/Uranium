## 3. RL 설정 (spec 042·033)

### 3.1 구조

- **actor-learner**(042 "구조")
  - 게임 여러 판(actor)이 관측을 보내면, 학습 호스트 GPU의 추론 서버가 배치로 행동을 정한다.
  - 학습 중인 에이전트의 결정은 T = 64 세그먼트(trajectory)로 큐에 들어가고, learner가 그 배치로 가중치를 고친다.
  - 새 가중치는 4 update마다 추론 서버에 복사된다(`weight_push_every = 4`).
- **한 프로세스**(AMB-042-10): `python -m uranium rl` 하나가 learner(PyTorch), 추론, 에이전트 서버, 게임 배정, 리그 관리를 맡는다. 에이전트 서버·게임 배정·trajectory 수집·리그는 `uranium._core`의 Rust 스레드가 GIL 없이 돈다.
- **추론 Broker**: 추론 서버(Rust Broker)가 여러 게임의 요청을 모아 배치로 모델에 넘긴다. 응답에는 정책 버전이 붙어 정책 지연(042-R4)을 잰다. 체크포인트 경로는 `URANIUM_SHARED_DIR` 기준으로 찾는다(020-R11). 그래서 `--logs`가 상대 경로면 시작에 실패하는 버그가 있었고, 10-31에 고쳤다.
- **lockstep 학습 게임**(001-R5): 게임은 우리 결정을 기다리며 진행한다. learner가 GPU를 쓰는 동안 추론이 늦어져도 결과는 그대로이고, 판의 벽시계 시간만 길어진다.
- **behaviour 기록**(AMB-042-4): actor는 고른 행동의 헤드별·joint log-prob만 남긴다. learner는 같은 관측으로 BC 모델을 다시 forward해 정확한 KL을 구한다(AMB-042-9).
- **privileged critic**(033-R6, 032-R11)
  - value head만 상대의 실제 상태 요약(privileged 입력)을 받는다. 정책 헤드·추론 경로에는 연결하지 않는다(맵핵 금지).
  - 보상 항목마다 value head가 따로 있다(033-R3): win, build, units, value. 채널 모드 `"scout"`에서는 build·units 채널이 r_scout·r_survive를 배운다(033-R11).
  - win_open head는 win의 V-trace target을 MSE로 배운다(042-R13, 가중치 0.5).

### 3.2 알고리즘과 기본 수치 (`config/rl.toml`, AMB-042-3)

| 항목 | 값 |
|---|---|
| 기본 알고리즘 | V-trace(IMPALA) off-policy 보정 + UPGO 보조 policy gradient. ρ̄ = c̄ = 1.0, γ = 1.0, TD(λ) 0.8(`rush-s3`부터 0.95) |
| 비교 알고리즘 | PPO: clip 0.2, 2 epoch, GAE λ 0.95. 3 seed 평균이 V-trace보다 3%p 넘게 높을 때만 채택 |
| KL(π‖π_BC) | 계수 = max(0.01, 0.1 × 0.5^(update / 20,000)). run마다 update 0부터 다시 센다 |
| 엔트로피 | 헤드별: action 3e-3, 나머지(delay, queued, selected, target_unit, target_loc) 1e-3 |
| 배치 | 레인 32 × T64(update당 약 2,016 step), 레인 그룹은 호스트 `.env` `URANIUM_RL_MICRO_LANES`(Windows CUDA 호스트 2, Linux ROCm 호스트 1) |
| 옵티마이저 | Adam, lr 3e-5(BC의 1/10), β1 0, β2 0.99, eps 1e-5, grad clip 1.0 |
| 손실 가중 | pg 1.0, upgo 1.0, value 0.5, win_open 0.5 |
| 큐 | 에이전트마다 4배치. 가득 차면 역압(게임이 기다림, 한 번 상한 120초, AMB-042-11). 정책 지연 32 update 넘으면 버림 |
| 판 벽시계 제한 | 7,200초(AMB-042-12). 넘으면 Timeout으로 학습에서 뺀다 |
| 체크포인트 | 30분마다, 전부 보존(061-R6, `keep_checkpoints = 0`) |
| 학습 리플레이 | 100판마다 1판 + 승자 불일치 판(042-R11) |

### 3.3 보상 (spec 033)

| 항목 | 정의 | 가중치 | 실제 사용 |
|---|---|---|---|
| r_win | 승 +1, 패 −1, 무 0(60분 시간 제한) | 1.0 | 모든 run |
| r_value | (적 손실 자원 − 아군 손실 자원) / 1000 차분 | 0.05 | AC1(C0). T1·셀프와 러시 run은 C1에서도 켰다(`r_value_stages = ["C0", "C1"]`). `t1self-s2`부터는 봇 판에만(`r_value_vs_model = false`) |
| r_build, r_units | z(사람 빌드 목표)와의 거리 변화 | 0.3, 0.3 | 쓰지 않음. 모든 run이 z 없이 돌았다(사용자 결정) |
| r_scout | 정찰로 처음 얻은 적 정보에 항목마다 한 번, 4:00 뒤 감쇠·8:00에 0, 판당 상한 | 0.15 | `rush-s2`부터(AMB-042-16). 모델 상대 판은 0.5배 |
| r_survive | 3:00~8:00 자기 SCV 수에 비례 | 0.1 | `rush-s2`부터, 봇 판만 |

- 033-R5: 보상 계산에 보이지 않는 적 정보를 쓰지 않는다. r_scout는 자기 시야와 시작 위치 목록만, r_survive는 자기 유닛만 쓴다.
- 033-R7: 한 결정의 보상은 그 결정 뒤 프레임들의 보상 합이다. r_win과 마지막 결정 뒤의 프레임 보상은 마지막 결정에 더한다.

### 3.4 리그·커리큘럼 (042-R5·R7)

| 에이전트 | 상대 샘플링(C2) | 목적 |
|---|---|---|
| Main | PFSP 50%, 셀프 35%, T1 15% | 최종 정책 |
| Main Exploiter | 현재 Main만 | Main 약점 발견 |
| League Exploiter | PFSP 전체 | 전략 다양성 |

| 단계 | 상대 | 다음 단계 조건 |
|---|---|---|

| C2 | 풀 리그(위 표), learner 시분할 Main 50%·Main Exploiter 25%·League Exploiter 25% | 없음 |

- **실제로 쓴 것**
  - C2(풀 리그)에는 가지 않았다. C0·C1에서는 Main만 학습한다(042-R7). 그래서 Exploiter 둘은 모든 체크포인트에서 BC 복사본이다.
  - AC1은 `--ac1-race zerg` 고정 설정(C0 고정, 투혼, T0 표준 저그만, 전환 없음)이다.
  - `t1self-s1`부터는 `start_stage = "C1"`, `auto_advance = false`로 상대 비중을 run 설정으로 정했다(AMB-042-13).
  - 스냅샷 상대: 250 update마다, 최근 4개 후보, 후보 안 PFSP f_hard(`t1self-s2`부터).
  - anchor: `t1self-s2`부터 `rush-s5`까지 모두 Checkpoint 1 RL(`ac1-vtrace-s1/ckpt-3133569`)이다.
  - 사다리 상대 선택: `f_var`(`rush-s1`·`s2`), 러시 그룹 `band`(`rush-s3`·`s4`), 러시 그룹 `fixed` 비중(`rush-s5`, 042-R19).
- `--init`(AMB-042-13): Main의 출발 가중치만 다른 체크포인트에서 가져온다. 옵티마이저·step·update·KL 계수·리그 상태는 새로 시작한다. KL 참조와 Exploiter 리셋 대상은 `--bc`(모든 run에서 BC `bc-s2e2-pt/ckpt-11387`)다.

### 5.2 3차 자문의 오류

- 3차 자문은 "stochastic이라 시드가 판을 가르지 않는다"고 보고, seed 44000(사다리 측정, AC1 막음 20/60)과 seed 43000(`rush-s3` c0, 막음 1/80)을 바로 비교했다.
- 실제로는 시드가 시작 위치를 정한다. OpenBW 패치(`0002-openbw-fixed-start-seed`)가 `URANIUM_SEED`를 난수 상태에 넣고, 평가 plan은 `seed_base + n`이라 연속 시드의 시작 위치가 강하게 상관된다.
- T0는 시작 위치를 고정 순서로 훑는다. 그래서 첫 공격 목표가 우리 본진인지(적중)가 시드로 정해진다.
  - seed 44000 묶음: 적중 0/30 → 저글링 도착 p50 4:08
  - seed 43000 묶음: 적중 33/40 → 첫 SCV 손실 p50 3:33
- 같은 seed로 비교하면 퇴보는 유의하지 않았다. 막음 AC1 6/80 vs `rush-s2` 끝 1/80, Fisher p 0.12.
- 영향
  - `rush-s4`가 AC1에서 다시 출발했다. 결과적으로 해는 없었다(두 계보에 차이가 없으므로).
  - `rush-s4` 판정 기준(33%·45%·55%)이 학습 조건보다 후한 값에서 나와 도달할 수 없는 값이었다. 학습 조건에서 AC1급 정책의 미니게임 승률은 처음부터 약 25~29%였다.
  - "도착 전 일꾼 손실 습관"도 틀렸다. AC1도 같은 조건에서 3:23~3:33부터 SCV를 잃었고, 그때 저글링이 실제로 와 있었다.
- 이 오류에서 조건 통제 측정(7.1절)이 나왔다.

### 5.3 왜 RL이 초반 러시 방어를 올리지 못했나

원인 분석, 4차·6차 자문을 합친 것이다.

| 원인 | 내용 | 근거 |
|---|---|---|
| 승패가 외생 변수로 정해짐 | 러시 판 결과는 상대 첫 목표가 우리 본진인지(도착 3:10 vs 4:00)로 대부분 정해진다. 늦은 도착이면 AC1·BC도 약 30%를 막고, 이른 도착이면 AC1도 약 9%만 막는다 | `m6_rl_rootcause.md` 2·4절 |
| 한 결정이 승패를 바꿀 확률이 작음 | 막으려면 배럭 1:40 → 벙커 약 2:45 → 마린 탑승 → SCV 수리 → 일꾼 동원이 다 맞아야 한다. 결정 단위(약 0.45초, 선택 12기, 결정당 명령 1개)로는 SCV 미세 조작이 거칠다 | 원인 분석 4절, 4차 자문 0절 |
| 방어 행동이 BC 사전분포에 드묾 | BC의 3:30 전 벙커 확률은 결정당 1% 미만, 판당 0.2~0.3이다. 무작위 탐색으로 성공이 너무 드물게 나온다 | F2 진단 |
| 신호 밀도 | 러시 방어 구간이 학습 step의 약 4%(`rush-s2`)였다. 미니게임·고정 비중으로 높였지만 결과는 같았다 | 2차 자문 |
| 상대 선택·자기 모방의 쏠림 | band가 쉬운 9풀히드라로 쏠렸다(러시 판의 47%). 이긴 판은 "러시가 늦고 약하게 온 판"(`judge_scv` p50 24~28)이라 자기 모방은 방어가 아니라 운을 복제했다. 적중 조건 승 판만 고른 뒤(`rush-s5`)에도 효과는 0이었다 | 원인 분석 3절, 6차 자문 1절 |
| 측정 잡음 | 10판 점검은 ±30%p, 30~40판은 ±15%p라 지난 "변화 없음·퇴보·개선" 대부분이 잡음 안이었다 | 원인 분석 5절 |
| 원인이 아닌 것 | KL(결정당 벌점 약 0.001~0.003), off-policy(ρ 평균 0.975, 버림 0), 엔트로피 붕괴, 학습 신호 경로 버그(판정 결과가 r_win으로 learner에 정상 도달) | F2, 원인 분석 3절 |
| privileged critic | 원인 분석은 critic이 결과를 미리 알아 advantage가 작다고 봤다. 4차 자문이 이를 바로잡았다: 행동과 무관한 baseline은 편향이 없고, 외생 분산을 빼 주므로 오히려 유리하다. critic은 바꾸지 않았다 | 4차 자문 0절 |

### 5.4 6차 자문의 결론: 보상만의 RL은 막다른 길

- `rush-s5` 점검(같은 128판): 이른 막음 c0 6/64 → c1 11/64 → c2 6/64. 늦은 23 → 21 → 22. Checkpoint 1 RL 4/64·14/64.
- 학습 판(재시작 뒤, 세 상대·적중 조건): 680판 87승(12.8%), 100판 블록마다 평탄.
- 자기 모방은 작동했지만 효과가 0이었다. 적중 승 124판을 골라 버퍼 256이 찼고 `sil_pos_frac`은 0.8~0.97이었다. 정책은 움직였지만(KL 0.042 → 0.076) 더 무작위해졌을 뿐이다.
- 적중 판에서 이긴 판은 벙커 64%(p50 3:44)·4분 SCV 14.3, 진 판은 벙커 14%·4분 SCV 5.6이었다. 필요한 행동은 있지만 드물다.
- 결론: 지금 BC 사전분포와 결정 단위에서 **보상만으로 초반 러시 방어를 올리는 RL은 막다른 길**이다. 근거는 run 5개, 약 2천만 step 동안의 평탄이다.
- 하루당 기대값 비교(자문 어림): RL 변형 약 +0.5%p/일, 교사 경로 약 +1.8%p/일과 재사용 자산.
- 다음 경로: 정찰 반응형 스크립트 교사 → botgen → BC 파인튜닝 → `rush-s6`. RL 변형은 돌리지 않는다.

### 7.2 실행 안전 가드 (042-R20, 060-R6, AMB-042-20, 11-05 22:41 master)

| 가드 | 내용 |
|---|---|
| 장치 치명 오류 즉시 종료 | CUDA illegal memory access·sticky 오류면 저장 없이 코드 70으로 종료한다. 메모리 부족·graph 캡처 오류는 제외. supervise가 LATEST에서 재시작한다 |

### 7.3 러시 미니게임 (042-R17, 020-R19, 033)

- 러시 그룹 판을 8:00에 끝내고 SCV ≥ 8이면 승으로 판정한다. `games.csv` `end_reason = RushJudge`, `judge_scv` 열.
- 효과: 방어 구간 step 밀도가 약 3배가 되고, 보상이 4분 안에 오고, 승률 표 = 막음 비율이 되며, 60분 무승부 낭비가 없어진다.
- RL에서는 효과를 보지 못했다(학습 판 막음 평탄). 기준(8:00 SCV ≥ 8)은 교사·DAgger 측정에 남았다.

### 7.4 자기 모방(SIL, 042-R16)

- 러시 그룹에서 이긴 판의 8:00까지 세그먼트를 버퍼에 담고, update 배치 32레인 중 4레인을 버퍼 세그먼트로 바꿔 SIL 손실(Oh et al. 2018)만 쓴다. `w_pg` 0.05, `w_v` 0.01, 버퍼 256 세그먼트(RAM 제약).
- 고르는 조건: 승 판만(`wins_only`), 상대 키(`select_keys`), 접촉 시각(`select_army_before_s`), 적중 조건(`select_start_hit`).
- 교훈: 조건을 통제하지 않은 자기 모방은 "운이 좋았던 판"을 복제한다. 적중 조건으로 제한해도 효과가 없었다. 이것이 6차 자문의 "보상·자기 성공만으로는 안 된다"는 판단의 근거가 됐다.
- 모방 학습 쪽(교사 혼합, DAgger)에서는 이 장치를 쓰지 않았다. `rush-s6`에서 다시 켤지는 정해지지 않았다.

### 7.5 조건 통제 섞기 (042-R18 `start_mix`, 042-R19 `fixed`)

- 러시 그룹 판만 seed를 다시 뽑아(최대 64회, game id 결정론) 첫 목표 적중 비율을 자연 1/3에서 0.5로 맞춘다. T0는 바꾸지 않는다. 리허설에서 판별 목표 추첨과 116/116 일치했다.
- 상대 비중을 승률 표 없이 고정 비중으로 뽑는다(`fixed`). band가 세 run 동안 의도대로 작동하지 않아 바꿨다.
- `rush-s5`에서만 썼다. 뒤 모방 경로의 plan은 섞기 대신 자연 시작 슬롯 seed를 쓰고, 점검은 128판으로 조건을 통제했다.

## 8. Checkpoint 1이 RL 가중치를 잇지 않은 이유와 다음 단계

### 8.1 잇지 않은 이유

- 6차 자문이 교사 경로의 파인튜닝을 **BC `bc-s2e2-pt/ckpt-11387`에서 시작**하도록 설계했고(041-R21 ①), 그 뒤 혼합·DAgger가 그 계보를 이었다. 자문 리포트에 BC를 고른 이유는 따로 적혀 있지 않다.
- 기록에서 확인되는 사정
  - 같은 조건 측정에서 RL 체크포인트는 러시 방어에서 BC보다 낫지 않았다. Checkpoint 1 RL 4/64·14/64, `rush-s5` 6M 6/64·22/64, BC 2/64·19/64(세션 막음)다.
  - RL이 올린 것은 T0 표준 저그 상대 승률(68% → 79%)이었다. 모방 경로가 노린 정찰·러시 식별·벙커와는 다른 능력이다.
  - 모방 경로의 게이트는 BC 기준값(val 500 72.37%, 128판 2/64·19/64, T0 stochastic 29%)으로 정했다.
  - RL 모델은 `last_failed` 실제 값으로 학습했고, BC 계열 평가는 0 고정이다. 출발점을 섞으면 이 조건도 맞춰야 한다.
- 결과적으로 RL 13 run(약 6,600만 step)의 가중치는 Checkpoint 1에 들어 있지 않다. RL이 남긴 것은 측정·가드·장치와 "보상만으로는 안 된다"는 진단이다.

### 8.2 다음 단계: `rush-s6`

- Checkpoint 1(`bc-dagger-r1/ckpt-1137`)을 `--init`과 `--bc`(KL 참조) 모두로 쓰는 RL run이다(041-R21 ⑥·R22, 9·10·12차 자문).
- KL 참조를 바꾸는 이유: BC를 KL 참조로 두면, BC에서 확률이 거의 0인 벙커·정찰을 KL이 다시 지운다.
- 출발 전 필요한 것
  - spec 042에 `rush-s6` 절이 아직 없다(041에서만 언급). spec 절 → 사용자 확인 → 코드 순서다.
  - `reports/checkpoint1.md` 9.2절의 사용자 확인 대기 항목
  - 대규모 배치 전 점검(출력 영향 결정 확정·구현, 표본 end-to-end)
  - `last_failed` 조건: Checkpoint 1은 BC 계열(평가 0 고정)이고 RL은 실제 값을 쓴다. `rush-s6`에서 어느 쪽을 쓸지 정해야 한다(기본안 미확정).
- 이 리포트 범위에서 정해지지 않은 것: 자기 모방·미니게임·조건 섞기를 `rush-s6`에서 쓸지, anchor를 무엇으로 둘지(지금까지는 Checkpoint 1 RL), 리그(C2)·다른 종족 복귀 시점.
