# 승패 헤드 학습 손실 상승(0.42 → 0.89) 원인 점검

- 날짜: 2026-10-27
- 계기: `reports/m6_arch_ablation_review.md` 부수 발견 8. 7개 비교 run(S1 10,000 update, data.seed 1, 32줄 × 64 step) 모두 승패 헤드(win, win_open) 학습 손실이 update 1k–2k에서 0.42까지 내려간 뒤 10k까지 0.89로 올라갔다. 리뷰는 "뒤쪽 순서 데이터의 승패 레이블 문제"를 의심했다(가설, 확신 중간).
- 실행: BC 본학습 전 점검(사용자 "계속 진행해", 권장안 "점검 먼저"). 독립 서브 에이전트가 읽기 전용으로 했다. 저장소·데이터·체크포인트는 고치지 않았고, GPU·학습 작업 없이 CPU만 썼다.

## 결론

**레이블 버그가 아니고, 데이터 순서에 따른 분포 변화도 아니다(둘 다 확신 높음).**

손실이 오른 이유는 **학습률이 줄었기 때문**이다.
- 승패 목표값은 한 게임 내내 같은 값(+1 또는 −1)이다. 한 게임은 한 줄에서 평균 약 50번의 update에 걸쳐 64 step씩 차례로 나온다.
- 학습률이 클 때는 모델이 앞 조각에서 그 게임의 답을 "외워" 다음 조각에서 바로 맞힌다. 그래서 학습 로그의 승패 손실은 **이미 일부를 학습한 게임**에 대한 손실이고, 실제 실력보다 훨씬 낮게 나온다.
- 학습률이 0에 가까워지는 후반에는 이 효과가 사라진다. 그러면 손실이 실제 수준으로 돌아간다. 처음 보는 게임 기준으로 약 1.0, 거의 동전 던지기 수준이다.

정리하면 다음과 같다.
- shard를 다시 build할 필요가 없다. win·win_open 목표값을 바꿀 이유도 없다.
- **학습 로그의 승패 손실은 진행 지표로 쓸 수 없다.** 승패 헤드의 실제 수준은 val(`bc-eval`의 `win_open_mse`)로 본다.
- 10,000 update 시점 val은 약 1.0이다. 승패 헤드가 처음 보는 게임에 통하는 것을 아직 거의 배우지 못했다는 뜻이다(별개의 남은 문제, 5절).

## 1. 학습 순서 재구성 (사실)

- **순서 규칙**(`uranium-data` `ShardSource::shuffled`·`order_file`, `Feeder::refill`)
  - shard 파일 2,069개를 키 순서로 놓고 seed 1로 섞는다.
  - 파일을 하나씩 읽으며, 그 안의 S1(train 분할) 게임을 파일별 seed로 섞는다.
  - 32줄은 게임이 끝날 때마다 다음 게임을 받고, update마다 64 step씩 진행한다.
- **재구성 검증**: run이 실제로 쓴 스캔 캐시(게임별 meta·step 수)로 같은 순서를 다시 계산했다.
  - 파일 목록 지문 `2069:aa19650834104968`이 체크포인트의 데이터 지문과 같다.
  - 학습 로그의 update별 누적 게임 수와 결과 없는 게임 수도 **10,000 update 모두 정확히 일치**했다.
- 0~10,000 update 동안 시작한 게임은 8,486개(S1 33,183개의 26%)다. 그중 1,671개(19.7%)가 결과 없음(`none`, value 가중치 0)이다. 결과 없는 게임은 손실의 분자와 분모에서 모두 빠진다(코드 확인).

- 20개 창 전체에서 stardata가 79~100%, 승 비율이 45~56%다. 즉 **어느 창이든 상수로 찍으면 MSE ≈ 1.0**이다. 0.42가 나올 만큼 쉬운 창도, 특별히 어려운 창도 없다.

  - 게임 길이: step 가중 평균 2,800~4,100 step

- 리뷰가 본 "결과 없는 게임 69 → 1,580"은 누적값이라 늘어 보인 것이다. 비율은 15~20%로 일정하다.

## 2. 손실은 데이터 위치가 아니라 학습률을 따른다 (사실)

- **5개 run 평균 win 손실**
  - update 1,500: 0.43 (lr 2.9e-4)
  - update 5,000: 0.64 (lr 1.5e-4)
  - update 7,000: 0.71 (lr 6.0e-5)
  - update 9,500: 0.86 (lr 3.7e-6)
  - 1k~10k에서 학습률과 손실의 상관은 −0.96이다.
- **같은 batch에서도 run마다 손실이 크게 다르다.** update 2008~2019에서는 모든 run이 같은 게임을 본다. 그런데도 all 0.41, ctx 0.46, lstm 0.51, terrain 0.57, outer 0.71이다. 데이터 탓이라면 비슷해야 한다.
- **1차 비교도 같은 모양이다.** Burn, 5,300 update 일정, 다른 데이터·순서였는데, 상승이 5,300 update 안에 압축돼 있다(gtrxl 0.53 → 0.90, lstm 0.68 → 0.95). 같은 위치(4k–5k)에서 PyTorch run은 학습률이 아직 커서 0.6대였다.

## 3. 고정 체크포인트로 같은 batch 다시 채점 (사실, CPU)

- 방법
  - `arch-abl-all-pt` 체크포인트를 업데이트 없이(eval 모드) 고정했다.
  - ckpt-2007에 저장된 데이터 위치에서 학습 batch를 그대로 다시 만들어 8 batch를 채점했다(결과 있는 usable step 11,524개). 코어 상태는 빈 상태에서 시작한다.
  - "본 게임"은 update 2007 시점에 이미 진행 중이던 게임이다(앞 조각을 학습함). "새 게임"은 그 뒤에 시작한 게임이다.

| 모델 | 본 게임 (win / win_open MSE) | 새 게임 (win / win_open MSE) |
|---|---|---|
| ckpt-2007 | 0.49 / 0.47 (상태가 쌓인 2~7번째 batch: 0.43 / 0.42) | **2.09 / 1.95** |
| ckpt-10000 | 1.17 / 0.99 | 0.95 / 0.96 |
| (참고) 학습 로그 update 2008~2015 | 0.35 / 0.35 | |

- 1k–2k 창의 batch는 쉬운 데이터가 아니다. 나중 모델(ckpt-10000)은 같은 batch에서 약 1.0을 낸다.
- ckpt-2007은 바로 앞에서 학습하던 게임은 자신 있게 맞히고, 처음 보는 게임은 자신 있게 틀린다. MSE 약 2는 정답률이 동전 던지기인데 예측값이 ±1에 가깝다는 뜻이다. 앞 조각에서 그 게임의 답을 외웠다는 직접 증거다.
- 한계
  - 새 게임 표본이 작다(1,617 step, 약 7줄).
  - 뒤쪽 창(ckpt-8716 위치) 채점은 하지 못했다. 이 PC 메모리가 부족해져 첫 실행이 8 batch에서 끊겼고, 다시 시작한 실행은 본학습을 앞두고 결과 없이 멈췄다. 뒤쪽은 2절의 Burn 비교가 보완한다.

## 4. 레이블 정확성 표본 점검 (사실)

- 방법
  - 손실이 높은 뒤쪽 창(update 8,500~9,800에 시작한 게임)에서 25개, 앞쪽 창(1,000~2,000)에서 15개를 결과 있는 게임 중 무작위로 골랐다.
  - 원본 .rep을 `uranium-replay convert`로 1.16.1 저장 형식으로 바꿨다.
  - 명령 스트림을 별도 파서로 읽어 **먼저 LEAVE(0x57)를 보낸 플레이어**를 직접 찾았다.
- 결과
  - 40개 모두 시점 플레이어가 테란이었다.
  - 40개 모두 저장된 result가 "먼저 나간 쪽이 패배"와 일치했다(bridge 판정 20개 포함).
  - 같은 TvT 게임의 두 시점은 서로 반대 레이블이었다. 플레이어 id 재매핑 문제는 나타나지 않았다.
- 한계
  - bridge 판정도 OpenBW가 나간 플레이어를 패배로 처리한 결과로 보인다. 그래서 leave 규칙과 완전히 독립된 신호는 아니다.
  - "먼저 나간 쪽이 이긴" 예외 게임(실수, 연결 끊김)은 이 방법으로 못 잡는다.
  - 표본은 대부분 stardata이고 scr_ladder는 1개다(scr_ladder 쪽은 확신 중간).

## 5. BC 본학습에 대한 의미

1. shard 재build와 목표값 변경은 필요 없다(확신 높음).
2. 학습 로그의 `value`·`win_open` 손실을 승패 헤드 진행 지표로 쓰지 않는다. 본학습(약 39,000 update)에서는 오래 낮게 보이다가 끝에서 오를 것이다. 그 모양은 문제 신호가 아니다.
3. 승패 헤드의 실제 수준은 중간 체크포인트의 val `win_open_mse`(`bc-eval`)로 추적한다.
4. 남은 질문(가설, 확신 낮음~중간): 상대 실제 정보를 받는 win 헤드조차 처음 보는 게임에서 상수 수준이다. 그 이유 후보는 다음과 같다.
   - (가) 10,000 update로는 학습량이 부족하다.
   - (나) 같은 게임 조각이 연달아 들어와, 진행 중인 게임의 답을 외우는 것이 일반화보다 쉬운 지름길이 된다.
   - (다) 손실 가중치 0.5가 작다.
   - (라) 사람 리플레이는 이른 GG(leave)가 많아 상태만으로는 결과가 잘 드러나지 않는다.

   바꾸려면 spec(041-R7·R19) 변경과 사용자 결정이 필요하다. RL 가치 학습과 항복 규칙(031-R12)이 이 헤드에 의존하므로 RL 착수 전에 다시 볼 가치가 있다.
5. 리뷰의 "뒤쪽 데이터의 레이블·결과 성질 문제" 가설은 기각한다.
