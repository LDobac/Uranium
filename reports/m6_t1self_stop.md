### 3-4. Steamhammer 프로토스 크래시 (질문 4)

- Windows 이벤트 로그: 11-03 03:29~08:03의 BWAPILauncher 크래시 11건이 **모두 같은 위치**다. 예외 0xc0000005(접근 위반), 문제 모듈 Steamhammer `module.dll`, **오프셋 0xbec66**. 결정적인 코드 버그다.
- 언제: 우리 세션 기록으로 상대가 사라진 프레임이 11,752~14,790(**게임 8.2~10.4분**), 판 벽시계 35~55초. 브리지는 이것을 상대 `Surrender`로 기록하고 hostd는 launcher 종료 코드 −1073741819로 Aborted 처리했다.
- 얼마나 자주: Windows 로컬 hostd의 Steamhammer 프로토스(Random → 프로토스 포함) 시작 27판 중 **10판 크래시(37%)**, 17판 정상 종료. 서킷브레이커 설정은 3연속 크래시로 격리돼 8판 거부됐다. 같은 봇의 테란·저그는 Windows에서 약 70판 크래시 0, Linux 호스트의 프로토스는 11판 크래시 0. 크래시 위치(8~10분) 전에 끝난 판은 정상이므로 실제 크래시 비율은 8분을 넘긴 판 기준으로 더 높다.
- 봇 로그: 크래시 판의 p1 `launcher.log`는 0바이트다(정상 판은 "Steamhammer 5.3.6 by Jay Scott"까지 남음). stdout이 파일 버퍼에 남은 채 프로세스가 죽은 것으로 보인다. `bwapi-data/write`도 비어 있다.
- 원인 함수는 찾지 못했다. Windows Steamhammer `module.dll`(10-16 빌드)에는 PDB가 없다(지금 빌드 스크립트 `tools/oss/common.ps1`은 `/Zi`·`/DEBUG`로 PDB를 남기지만 Steamhammer는 그 전에 빌드됨). 다시 빌드하면 오프셋이 바뀌므로, 찾으려면 PDB를 남기는 재빌드 → 재현 → cdb로 스택 확인이 필요하다. Windows MSVC 빌드(BWAPI 4.2 포크, Linux 포팅 패치 0006 적용)에서만 나고 GCC(Linux) 빌드에서는 나지 않으므로 MSVC 최적화에서 드러나는 정의되지 않은 동작이나 BWAPI 4.2와의 차이가 후보지만 확인하지 않았다. 봇은 고치지 않았다.
- 참고: Linux 호스트의 Iron Aborted 4판(종료 코드 없음, 신호로 끝남)과 Steamhammer 테란 1판은 조사하지 않았다.

## 4. 가장 가능성 높은 원인

1. **셀프플레이 상대가 "지금의 Main" 하나뿐**이라, 양쪽이 같이 수동적으로 바뀌면 그것을 벌하는 상대가 없다(증거 강함: 마지막 대 출발 0-10, 자기끼리 9/10 무승부).
2. **그 표류의 방향을 정한 것은 보상 구성**일 가능성이 크다: 셀프 판이 학습 step의 70% 이상을 차지하고 그중 무승부(r_win 0)가 늘수록 기울기는 r_value(자기 손실 벌점)로만 정해진다. 결과 행동(병력 최소, 터렛·일꾼·건물, 손실은 SCV·터렛)이 "잃지 않기"와 맞는다(증거 중간: 시간 순서·신호 비중·행동은 맞지만 r_value 없이 같은 조건 대조는 없음).
3. **T1 신호가 너무 약하다**: T1에게 거의 다 져서(특히 3~5분 러시) r_win이 거의 상수이고, step 비중도 24~33%라 셀프 쪽 표류를 되돌리지 못했다. 그 결과 셀프 습관이 T1 초반 빌드까지 번졌다(c3M 배럭 반감, 배럭 없는 판 16/30).
4. KL 급등(update 1,480~1,500)은 원인이 아니라 행동 변화 뒤에 온 불안정 사건이다. KL 계수·정책 지연·엔트로피는 주원인이 아니다.

## 5. 대응 선택지 (미결정)

| 선택지 | 기대 효과 | 대가·위험 |
|---|---|---|
| A. 셀프 비중 낮추기(예: 0.5 → 0.2~0.3) | 표류 속도·step 비중 감소 | T1 판이 대부분 지는 판이라 학습 신호가 더 약해짐. 셀프를 줄여도 상대가 "지금의 자기"면 같은 표류가 느리게 남음 |
| B. 셀프 상대를 과거 스냅샷과 섞기(출발 체크포인트·c1M 같은 고정 상대 포함, 042 C2의 PFSP 방식을 C1에 일부 도입) | 붕괴 방지의 정석. 출발점에 지는 정책은 바로 벌받음 | spec 042 C1 정의 변경 필요. 스냅샷 추론 서버 메모리·처리량 |
| C. 셀프플레이 판에서만 r_value 끄기(T1 판은 유지) | 무승부 판의 유일한 신호가 사라져 "잃지 않기" 압력 제거 | 무승부 판은 거의 신호가 없어짐(학습 step 낭비). r_value 기여가 실제로 얼마인지는 이 대조로만 확인 가능 |
| D. 무승부 처리 바꾸기(예: 시간 제한 무승부를 양쪽 소폭 음수, 또는 더 짧은 셀프 시간 제한) | 시간 끌기·안 끝내기에 직접 압력 | 033 r_win 정의 변경(사용자 결정). AC1에서 T0 상대 무승부 대부분은 사실상 패배였던 점과 함께 정해야 함 |

## 6. 확인하지 못한 것

- r_value를 끈 같은 조건 대조 실험(원인 2의 크기).
- update 1,480~1,500 불안정 사건의 직접 계기, value head별 손실.
