## 분석 (2026-10-15, M1(a))

### 환경
- GPU: `AMD BC-250 (RADV GFX1013)`, Mesa 26.2.4, Vulkan 1.4. `shaderFloat16 = true`, subgroup 64, DEVICE_LOCAL heap 10.33 GiB (`reports/vulkaninfo_bc250.txt`).
- Burn **0.22.0** (crates.io 최신 안정판). 0.22에서 API가 바뀜: `Tensor<D>`가 백엔드 제네릭을 갖지 않고 `Device`(런타임 선택)로 백엔드를 고름. CPU 백엔드 `ndarray`는 deprecated → `flex` 사용.

### 결과 요약
- **미지원·부정확 연산 없음.** 032에 필요한 모든 연산(scatter-add, gather, attention bias, GRU 루프, ConvTranspose, Gumbel-max)이 Vulkan에서 동작하고 CPU(flex) 결과와 일치(상대오차 ≤ 1e-6, f16 matmul 4.5e-4).
- **최대 처리량**: matmul f32 ≈ 2.2 TFLOP/s, f16 ≈ 3.3 TFLOP/s (4096²).
- **032-AC2 (추론 B16·N256 ≤ 40ms) 미달**: `act_approx` 87ms (헤드 1–5 제외 근사). 내역(B16 fwd): Transformer 43ms, 128² conv stem 10.5ms + 다운샘플, ConvT 디코더 10.4ms, LSTM step 5ms.
- **attention distance bias 역전파가 비정상적으로 느림**: fwd 8ms → fwd+bwd 310ms. 원인 추정: bias 테이블(8×32)에 B·N²(≈100만) 개 인덱스의 gradient를 scatter-add로 모으면서 원자 연산 경합. → 구현 방식 변경 필요(예: bucket one-hot과 matmul, 또는 bucket별 사전 합산).
- **학습 처리량 추정 (fwd+bwd, 프레임당)**: Transformer 9.3ms + 공간 인코더 ≈6.5ms + 위치 디코더 7.1ms + 포인터 1.4ms + LSTM 0.2ms ≈ **25ms/프레임 → 약 40 프레임/s, 하루 약 350만 프레임** (bias 문제 해결 가정, f32).
  - BC 데이터(약 3만 게임 시점 × 4천 판단 ≈ 1.2억 프레임) 1 epoch ≈ 34일 → 현재 설계로는 학습이 매우 느림.

### 대응 후보 (사용자 결정 필요, spec 032 변경 사항)
1. f16 혼합 정밀도(지원 확인됨, matmul 1.5배) — 032-R8 활성화.
2. 공간 입력을 128² → 64²로 줄이고 위치 출력만 128²로 업샘플(공간 연산 약 1/4).
3. 엔티티 인코더 축소(d 256→192 또는 3층→2층), 패딩 대신 실제 엔티티 수 기준 배치.
4. BC 학습 시 프레임 샘플링(예: 게임당 일부 구간만 학습).
5. attention bias 구현 교체(필수).
