## 4. 단계별 상세

### 4.0 준비 (10-23 ~ 10-27)

- **PyTorch 전환**(AMB-000-4, 10-23 결정, `reports/pytorch_port.md`)
  - 학습·추론을 Burn에서 Python 3.14 + PyTorch로 옮겼다. 데이터 공급·저장소·실행 루프는 Rust(`uranium._core`)에 남겼다.
  - 같은 가중치·입력에서 Burn과 출력이 1e-5, gradient가 상대 1e-4 안에서 맞는 것을 확인했다.
- **2단계 최적화**(032-R19 같은 수식만, `reports/pytorch_opt.md`)
  - Linux ROCm 호스트 BC update가 23.5초 → 10.0초가 됐다. 위치 헤드 곱-합, 거리 bias 표, split-K 행렬곱, 직접 작성한 엔티티 attention 커널(CUDA·HIP 같은 소스)을 썼다.
  - Windows CUDA 호스트는 4.7초 → 2.0초, 10-28 그래프 캡처·channels-last 등으로 1.32초가 됐다.
  - 추론 지연은 22~36 ms → 1.3~6.3 ms다.
  - 운영 문제도 고쳤다: Windows 힙 페이지 폴트(mimalloc), glibc arena 단편화(arena 2개 제한, 060-R3).
- **코어·구조 비교**(032-R17 ⑥·R20, `reports/m6_core_ablation_pt.md`, `reports/m6_arch_ablation_pt.md`)
  - LSTM과 GTrXL, 구조 변형 다섯을 각 10,000 update 학습하고 평가 4,200판·val 500을 돌렸다(10-24 21:3x ~ 10-27 14:18).
  - 사용자 결정(10-27): GTrXL에 구조 변형 넷 모두 켬, 학습 시퀀스 T = 64.

### 4.1 BC 본학습 1 epoch (10-27 16:31 ~ 10-29 11:46)

- **무엇을, 왜**
  - 사람 리플레이(동결 데이터 2,069 파일)로 041 2단계 학습을 했다.
  - S1은 전체 맵 39,096 update, S2는 대상 맵 11,387 update다.
  - 대조군 (A)는 대상 맵만 11,387 update다. 041-R5 ablation이다.
- **장비**
  - CUDA 작업자(우선순위 10)와 Linux ROCm 작업자 둘이 run을 양보하며 이어 받았다.
  - 사용자가 학습 PC를 쓰는 동안에는 ROCm 호스트가 S1을 맡았다(update당 약 13초 vs CUDA 1.3~2초).
  - 10-28 01:13~10:52에 측정으로 학습 PC가 빠져 CUDA 환산 약 7.9시간을 잃었다(사용자 지적).
- **시간**
  - S1: 10-27 16:31 ~ 10-29 06:09(37.6 h)
  - S2: 06:09 ~ 11:11(5.0 h)
  - (A): 10-29 11:46에 끝(43.3 h)
- **결과**(`reports/m6_bc_eval.md`)
  - 대상 맵 test 1,199게임에서 action top-1은 (B) S2 71.45%, (A) 68.98%다. 모든 지표에서 (B)가 앞서 AC1·AC3 통과다.
  - T0 600판: argmax 0/300, stochastic 88/300(29%). 매치업은 테란 17%, 프로토스 16%, 저그 55%라 AC2(매치업마다 ≥ 50%)는 저그만 통과했다.
- **실패와 원인**
  - argmax는 사람의 랠리 연타를 배워 선택·우클릭 고리에 갇힌다(10-21 원인 확인, 고칠지는 사용자 결정으로 남음).
  - argmax 판의 승자 불일치 90판은 OpenBW가 진 쪽 원격 클라이언트를 끊어서 생겼다. OpenBW 패치 0015(011-R22)로 고쳤다.

### 4.2 BC 두 번째 epoch (10-29 16:47 ~ 10-31)

- **무엇을, 왜**: 041-R20(10-29 사용자 결정)에 따라 S1을 한 번 더 학습하고 S2를 다시 했다.
  - `bc-s1e2-pt`: 39,094 update, lr 절반, data seed 2, 10-29 16:47 ~ 10-30 15:06(22.3 h)
  - `bc-s2e2-pt`: 11,387 update, 10-30 16:12 ~ 10-31 06:35(14.4 h)
- **측정**: S1 체크포인트마다 val 500게임 채점과 T0 stochastic 100판을 돌렸다. 처음에 둔 자동 멈춤 규칙은 사용자 결정으로 없앴다.
- **결과**(`bc-s2-pt` → `bc-s2e2-pt`)

  | 지표 | `bc-s2-pt` | `bc-s2e2-pt` |
  |---|---|---|
  | test top-1 | 71.58% | 72.15% |
  | T0 stochastic 300판 | 29% | 39% |
  | 저그전 | 55% | 66% |

  - 10-31 사용자 결정으로 `bc-s2e2-pt/ckpt-11387`이 RL 출발점과 KL 참조가 됐다.
  - val 500 top-1은 72.37%다. 11-06에 따로 채점했고, 이후 모든 교사 경로 비교의 기준이 됐다.

### 4.3 RL 준비 (10-31 ~ 11-01)

  - 시야 밖에서 기억하는 적 건물을 공격 대상으로 허용했다(잔상 클릭).

## 9. 남은 문제·다음 단계

### 9.1 남은 문제

1. **운영형 상대 벙커 습관**(G2 실패, 12차 자문 1절)
   - 교사는 정찰이 본 미완성 풀의 HP로 착공 시각을 추정해 러시와 운영형을 가른다(①a).
   - 모방 모델은 풀 HP를 읽지 못한다(10차 가림 실험). 그래서 "정찰이 본진에서 풀을 봄 → 벙커"만 배웠다.
   - 운영형 12해처리·11풀도 2:00~2:20에 풀을 놓으므로, 그 풀을 본 모델은 러시 때와 똑같이 벙커를 짓는다.
   - 교사 클론(교사 판만 5 epoch)도 28~31/40이다. 원인은 사람 데이터가 아니라 단일 프레임 근거를 읽어야 하는 모방 자체의 한계다. DAgger는 상태를 더 줄 뿐 그 특징을 읽게 해 주지 않는다.
   - 교사가 같은 벙커 지시를 반복하는 것도 레이블 질량을 키운다. dagger r1은 판당 7.3, botgen은 1.9다.
2. **이른 조건 막음 20/64**
   - 상대 첫 목표가 우리 본진이면 저글링이 약 3:10에 온다. 이때 막는 비율이 여전히 낮다.
   - 교사는 46/64를 막는다.
3. **명령 이력 오염**(11차 자문 4절 ①)
   - BC는 메모리의 직전 행동과 유닛별 last_action을 레이블로 채운다. 그래서 dagger 스텝의 상태는 모델 것이지만 명령 이력 특징은 교사 것이다.
   - 이번에는 정찰이 올라서 걸림돌이 아니었다. 다음 수단은 "메모리를 모델이 실제로 실행한 명령으로 채우는 shard 필드"다(이번 범위 밖).
4. **강한 T1 봇 상대 0승 수준**
   - Stardust 0/50, Iron 0/50, ZZZKBot 1/50이다.
   - 1차 자문은 Iron·Stardust 상대는 훨씬 많은 계산이나 데이터가 필요하다고 봤다. Steamhammer 프로토스·테란에도 0승이다.
5. **TvT·TvP**
   - G4를 TvZ로 바꾼 것은 교사(TvZ 전용, 가스 없음) 데이터가 TvT·TvP 개방을 덮어 퇴보했기 때문이다(10차 자문). 범용성 회복은 리그·RL 단계 과제로 남았다.
   - 참고로 UAlbertaBot 프로토스·테란 상대는 조금 올랐다.
6. **그 밖에 이전부터 남은 것**
   - argmax 랠리 연타 고리. 평가는 계속 stochastic이다.
   - T0 저그의 정제소 기억 버그와 60분 무승부. T0는 사용자 결정으로 그대로 둔다.
   - Steamhammer 프로토스 Windows 빌드 크래시
   - 그림자 교사의 거짓 양성은 records에 통계가 없어 재지 못했다(12차 자문 1-4).
