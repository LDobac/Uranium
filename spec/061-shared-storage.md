## Purpose
여러 학습 호스트(Linux Vulkan 호스트, CUDA 호스트)가 체크포인트와 학습 데이터를 네트워크 공용 드라이브(SMB, LAN 또는 VPN 경유)로 공유하도록 규칙을 정한다. 학습할 PC는 공용 드라이브에서 체크포인트를 받아(pull) 학습하고, 결과를 다시 올린다(push).

## 확정 사항 (2026-10-15, 사용자 결정)
| 항목 | 결정 |
|---|---|
| 공용 드라이브 | SMB(Windows/NAS 공유). Linux는 cifs 마운트, Windows는 드라이브 문자나 UNC 경로 |
| 동시 학습 | **학습 실행(run) 단위로 한 PC만** 학습한다. 서로 다른 run은 다른 PC에서 동시에 진행할 수 있다 |
| 학습 데이터 | 원본은 공용 드라이브에 두고, 학습 호스트는 필요한 shard를 로컬 캐시로 복사해 쓴다 |
| 학습 호스트 OS | Linux와 Windows 모두 지원 |
| 공유 제공 PC | Windows CUDA 호스트가 SMB 공유를 제공한다. 이 호스트는 Linux 호스트들과 다른 장소에 있고 VPN(WireGuard)으로 연결된다. 따라서 공용 드라이브 접근은 인터넷 대역폭과 VPN 연결 상태에 좌우된다(R11). 주소·계정 등 접속 정보는 spec에 쓰지 않고 각 호스트의 `.env`·마운트 설정에만 둔다(001-R9) |
| 원격 전송 정책 | 원격 구성에 맞게 pull·push 정책을 보강한다(R11, AMB-061-1 결정) |
| 공유 제공 PC의 캐시 | 공유를 제공하는 PC가 학습할 때는 복사 없이 원본을 바로 읽는다(R12, AMB-061-2 결정) |

## Scope & Non-goals
- 범위:
  - 체크포인트, 리그 스냅샷, 승격 체크포인트의 저장과 배포
  - BC 데이터셋(shard, `.rep`) 저장
  - 학습 실행 잠금
  - 로컬 캐시
- 비범위:
  - 여러 GPU가 하나의 모델을 함께 학습하는 분산 학습
  - 게임 데이터(MPQ·CASC 추출물·맵). 이 파일은 각 게임 호스트가 `config/assets.toml` 해시로 검증한다(011-R13).

Ctrl+C(SIGINT)는 현재 run을 체크포인트·push·잠금 해제한 뒤 작업자까지 끝낸다. 작업자는 `workers/<host>.json`에 자기 상태(우선순위, 백엔드, 현재 run, 갱신 시각)를 1분마다 쓴다(자식 학습 중에도) |
| 061-R14 | **MUST** 양보 요청(preemption, 2026-10-18 사용자 결정). 잡을 run이 없고 다른 PC의 작업자가 큐의 run을 돌리고 있으며 자기 우선순위(`--priority`, 빠른 장비가 큼)가 그 PC 작업자보다 높으면, 작업자는 `locks/<id>.yield`(요청 host·우선순위·시각)를 쓴다. 양보 대상은 작업자가 돌리는 run뿐이다(잠금 주인 host의 `workers/<host>.json`이 그 run을 가리킬 때). 사용자가 직접 실행한 `bc --run`(작업자 상태 파일이 그 run을 가리키지 않음)에는 양보 요청을 쓰지 않는다(사용자 결정 2026-10-19). 그 run을 돌리는 학습은 매 update 끝에 요청 파일을 확인하고, 다른 host의 요청이면 체크포인트·push·잠금 해제 후 종료 코드 76으로 끝난다. 그 작업자는 다른 run으로 가거나 기다린다. 요청이 있는 run은 요청 host만 잡을 수 있고(예약), 요청 host가 잡으면 요청 파일을 지운다. 요청이 30분 안에 처리되지 않으면 만료로 본다. 만료 판정은 R5 잠금 만료와 같은 방식이다(2026-10-19): 작업자가 자기 단조 시계로 같은 요청 내용(host·우선순위·시각)을 30분 동안 연속 관측했을 때만 만료로 보고 그 요청 파일을 지운다. 파일 mtime이나 기록된 시각을 비교하지 않는다. 내용이 바뀌거나 읽기에 실패하거나 관측이 끊기면 처음부터 다시 관측한다. 한 run에는 한 순간 한 잠금 소유자만 있다(R5). **보완(2026-10-19, H, AMB-061-6)**: ① 요청 host의 작업자가 종료하거나 다른 run을 잡으면 자기가 쓴 요청 파일을 지운다 ② 양보 중 최종 push가 실패하면(공용 드라이브 접근 불가로 미뤄짐, R11-3) 잠금을 놓지 않고 학습을 계속하며, 다음 push 시점에 push가 성공한 뒤 양보한다. 잠금을 쥔 채 76으로 끝나지 않는다 ③ 옛 계통 배제: 이어받은 쪽이 새 체크포인트를 push한 뒤에는, 양보한 PC의 로컬 캐시에 남은 미push 체크포인트를 R11-5 복구 대상으로 쓰지 않는다(R11-5 계통 조건) |
| 061-R15 | **MUST** 장비 기록: 학습은 `runs/<id>/devices.jsonl`에 세션 시작·체크포인트·종료마다 JSON 한 줄을 덧붙인다. run마다 장비별 update 구간과 비율을 이 파일로 집계한다(코어 비교 등 공정성 확인, 032-R17). 줄 형식(2026-10-19 명시): 모든 줄에 `event`(`start` / `checkpoint` / `stop`), `host`(호스트 라벨), `step`, `time`(Unix 초)을 쓴다. `start` 줄에는 `backend`, `precision`, `core`, `stage`를 더하고, `stop` 줄에는 `reason`(완료, Ctrl+C, 잠금 상실, 양보 등)을 더한다. 백엔드·정밀도는 같은 host의 직전 `start` 줄 값이다. 구간 집계: 한 세션은 `start`부터 다음 `start`(다른 세션) 전까지의 줄이다. `stop` 없이 끝난 세션(크래시·강제 종료)은 마지막 `checkpoint` 줄 step까지만 그 장비 구간으로 세고(그 뒤 update는 체크포인트에 남지 않아 다음 세션이 다시 한다), 다음 세션의 `start` step이 더 작으면 거기서 자른다 |

### 061-R4 push 순서
1. `ckpt-<step>.tmp-<host>/`에 모든 파일과 `manifest.json`(파일별 SHA-256)을 쓰고, 파일마다 fsync한 뒤 클라이언트 캐시를 거치지 않고 다시 읽어 manifest와 대조한다(040-R17과 같은 방식, 2026-10-20 사용자 결정, AMB-040-12). 다르면 push하지 않고 다음 시도로 미룬다(R11-3).
2. 디렉터리를 `ckpt-<step>/`로 rename한다.
3. 마지막에 `LATEST` 파일을 임시 파일 쓰기 → rename 방식으로 갱신한다.

### 061-R5 잠금 규칙
- 잠금 파일 `locks/<run_id>.json`에는 host, pid, 시작 시각, 마지막 heartbeat를 기록한다. heartbeat는 1분마다 갱신한다.
- 유효한 잠금이 있으면 다른 PC는 같은 run의 학습을 거부한다(종료 코드 75). 예외는 아래 수동 `--take-over`다.
- 정상 종료(042-R10)할 때는 push 뒤에 잠금 파일을 지워 해제한다. 그래서 바로 재시작해도 `--take-over`가 필요 없다(2026-10-16).
- **수동 인수 `--take-over`(2026-10-19 사용자 결정 D-d, AMB-061-6)**: 다른 PC의 잠금은 사용자가 `--take-over`로 명시할 때만 넘겨받는다. `--take-over`는 잠금 상태(유효·만료)를 기다리지 않고 **즉시 인수**하고 경고를 출력한다. 경고 내용: 잠금 주인이 아직 살아 있으면 그 학습은 다음 heartbeat 갱신 때 잠금이 자기 것이 아님을 보고(Lost) push 없이 멈추고, 그 PC에만 있던 미push 체크포인트는 잃을 수 있다(R11-4). 사용자가 상대 PC가 멈췄음을 확인하고 쓰는 옵션이다.
- **자동 인수의 만료 판정(2026-10-19, H-3, AMB-061-6)**: run 큐 작업자(R13)의 자동 인수에만 쓴다. 작업자가 **자기 단조 시계(monotonic clock)로**, 잠금 파일의 heartbeat 내용(host, pid, 마지막 heartbeat 값)이 `stale_after`(10분) 동안 바뀌지 않음을 **연속으로 관측**했을 때만 만료로 보고 넘겨받는다. 파일 mtime이나 기록된 시각을 자기 시계와 비교하지 않는다(PC 사이 시계 차이에 영향받지 않게). 관측 중 내용이 바뀌거나 읽기에 실패하면(R13 "모름") 관측을 처음부터 다시 한다.
- **종료 코드 75**: 학습이 잠금을 얻지 못해 끝날 때(다른 PC의 유효 잠금, 동시 획득 경쟁에서 짐, 다른 host가 예약한 run(R14)) 75로 끝난다. 감시 프로세스와 작업자는 75를 재시작하지 않는다(060-R6).

### 061-R11 원격 전송 규칙
1. **shard 재사용**: 데이터셋 shard는 한 번 만들면 바꾸지 않는다. 학습 시작 시 필요한 shard 중 로컬 캐시에 없거나 manifest 해시가 다른 것만 받는다.
2. **재개 가능한 pull**: 파일은 `<name>.part`로 받고, SHA-256 검증을 통과하면 최종 이름으로 rename한다. 중단되면 다음 실행에서 이미 완료된 파일은 건너뛴다.
3. **push 실패 시 계속 학습**: 공용 드라이브에 접근할 수 없으면 학습은 멈추지 않는다. 경고를 남기고 다음 push 시점(R4)마다 다시 시도한다. push되지 않은 로컬 체크포인트는 push에 성공할 때까지 정리(R6) 대상에서 뺀다.
4. **연결 복구 시 잠금 재확인**: 끊긴 동안에는 heartbeat를 갱신하지 못한다. 연결이 돌아오면 잠금 파일을 다시 읽는다. host·pid가 자기 것이 아니면(다른 PC가 `--take-over`로 인수) 즉시 학습을 멈추고 push하지 않는다.
5. **미push 체크포인트 복구**: 재시작할 때 다음 세 조건이 모두 맞으면 로컬 체크포인트를 먼저 push하고 거기서 재개한다.
   - 잠금 파일의 마지막 소유자가 이 호스트다(그사이 인수가 없었다).
   - 로컬 캐시에 공용 드라이브 `LATEST`보다 step이 큰 체크포인트가 있다.
   - 그 체크포인트가 manifest 검증을 통과한다.
   - 계통 조건(2026-10-19, R14 ③, AMB-061-6): 공용 드라이브의 현재 `LATEST`가 그 로컬 체크포인트의 계통(이 호스트가 재개했거나 push한 체크포인트의 연쇄)에 속한다. 즉 `LATEST`가 그 로컬 체크포인트의 조상이다. 그사이 다른 호스트가 다른 계통의 체크포인트를 push했으면 로컬 미push 체크포인트는 쓰지 않는다.
6. **정상 종료 시 push 실패**: 경고를 남기고 미push 체크포인트를 로컬에 둔 채 종료한다. 다음 시작 때 5로 처리한다.

## Acceptance Criteria
- 061-AC1: PC A에서 pull → 학습 → push → PC B에서 pull → resume을 했을 때, 불러온 가중치·옵티마이저·학습 상태(step, 데이터 위치, 데이터 RNG)가 비트 단위로 일치하고, 이어서 진행한 학습 손실 곡선이 끊김 없이 이어진다. "끊김 없이"(2026-10-19 사용자 결정, G-D7, AMB-061-4): A와 B가 **같은 장비**(같은 PC)이고 Burn autotune 캐시를 유지·고정한 경우(041-R15)에는 끊지 않고 학습한 경우와 손실이 비트 단위로 같다. 이 비트 동일 요구는 Flex와 Vulkan 호스트에만 적용하고, **CUDA 호스트는 같은 PC여도 032-AC1 허용 오차(1e-2)로 판정한다**(사용자 결정 2026-10-19: CUDA atomic add 연산과 Windows autotune 캐시 미저장으로 실행마다 결과가 달라짐, 041-R15·`reports/m6_bc_preflight.md` 5차). 다른 장비이거나 autotune 캐시가 다르면 032-AC1 허용 오차(Vulkan·Flex 1e-4, CUDA가 끼면 1e-2) 안이다. dropout RNG는 저장할 수 없어 비교에서 제외한다(dropout 0인 설정으로 판정).
- 061-AC2: push 도중 강제 종료해도 `LATEST`는 항상 manifest가 검증되는 완전한 체크포인트를 가리킨다(장애 주입 테스트).
- 061-AC3: 유효한 잠금이 있는 run을 두 번째 PC에서 `--take-over` 없이 시작하면 명확한 에러(종료 코드 75)로 거부된다. 만료된 잠금도 `--take-over` 없이는 인수되지 않는다(run 큐 작업자의 자동 인수(R13)는 예외). `--take-over`는 즉시 인수하고 경고를 출력하며, 원래 소유자는 다음 heartbeat에서 push 없이 멈춘다(R5, R11-4). 작업자 자동 인수는 R5 단조 시계 관측으로만 일어나고, 잠금 파일 mtime을 바꿔도 결과가 달라지지 않는다.
- 061-AC4: Linux(cifs 마운트)와 Windows(드라이브 문자) 경로 모두에서 AC1–AC3이 통과한다.
- 061-AC5: Vulkan 호스트에서 저장한 체크포인트를 CUDA 호스트에서 불러왔을 때(반대 방향도 같다), 불러온 가중치·옵티마이저 상태가 저장한 값과 비트 단위로 같고, 같은 입력의 forward 출력 차이는 032-AC1 기준(Vulkan·Flex ≤ 1e-4, CUDA가 끼면 ≤ 1e-2) 안이다(2026-10-19 사용자 결정, G-D7, AMB-061-4).
- 061-AC6: 공용 드라이브 접근 차단(장애 주입) 상태에서 학습이 계속되고, push가 재시도된다. 미push 체크포인트는 정리되지 않는다. 접근이 복구되면 push된다. 차단 중 강제 종료 후 재시작하면 R11-5 조건에서 로컬 체크포인트를 push하고 그 step에서 재개한다. 차단 중 다른 PC가 `--take-over`했다면 복구 후 원래 PC는 push 없이 멈춘다.
- 061-AC7: R12 로컬 모드에서 pull이 캐시에 shard를 복사하지 않는다. 원본 shard 하나를 변조하면 manifest 검증 실패로 학습 시작이 거부된다.
- 061-AC8: 작업자 둘(가짜 학습, Flex)이 같은 큐에서 서로 다른 run을 잡고, 한 run에 두 소유자가 생기지 않으며, 양보 요청 시 낮은 우선순위 쪽이 체크포인트·잠금 해제 후 넘기고 요청한 쪽이 이어받는다. Ctrl+C로 멈춘 run을 다른 작업자가 이어받는다.
- 061-AC9: Windows CUDA 호스트와 Linux Vulkan 호스트에서 짧은 시험 run 두 개로 잡기, Ctrl+C 후 이어받기, 양보 요청, 강제 종료 후 watchdog 재시작을 확인하고 `devices.jsonl`에 장비 구간이 남는다.

## Risks & Open Questions
- R14 수동 실행 run 판별의 한계(2026-10-19): 양보 대상 여부는 잠금 주인 host의 `workers/<host>.json`이 그 run을 가리키는지로 판단한다. 작업자가 강제 종료되면 상태 파일이 `run=X`인 채로 남으므로, 그 host에서 X를 `bc --run`으로 수동 실행하면 다른 작업자가 양보를 요청할 수 있다. 대응: 수동 실행 전에 남은 상태 파일을 지우거나, 그 host의 작업자를 다시 띄워 상태 파일을 갱신한다(`docs/commands.md`).
- SMB 위에서의 rename 원자성은 서버 구현(Windows, Samba, NAS)에 따라 다를 수 있다. 2026-10-15 실제 공유(Windows SMB, Linux cifs 3.1.1 마운트, VPN 경유)에서 확인한 결과는 다음과 같다. M5에서 장애 주입으로 061-AC2를 정식 검증한다.
  - tmp→최종 디렉터리 rename 후 SHA-256 검증: 통과
  - 기존 파일 위로 rename(`LATEST` 갱신): 통과
  - 비어 있지 않은 기존 디렉터리 위로 rename: 거부됨(안전)
  - 서버 대소문자: 구분 안 함
  - 파일 mtime과 로컬 시각 차이: 0초
- 네트워크 대역폭에 따라 shard pull 시간이 길 수 있다. 2026-10-15 실측은 Linux 호스트 ↔ 공용 드라이브 VPN 경유 쓰기 약 42MiB/s, 읽기 약 40MiB/s다. 600GB를 처음 받는 데 약 4~5시간이 걸린다. R11-1(shard 재사용)과 R11-2(재개)로 완화한다.
- 공용 드라이브를 제공하는 호스트가 꺼지거나 VPN이 끊기면 다른 호스트는 pull·push를 할 수 없다. 이미 캐시한 데이터로 학습을 계속하고 R11-3~6으로 처리한다. 캐시에 없는 shard가 필요한 새 학습은 시작할 수 없다.
- R12 로컬 모드는 설정값으로 켠다. 경로만 보고 자동 판별하지 않는다(네트워크 드라이브 문자·UNC·마운트 종류 판별이 OS마다 불안정하다).
