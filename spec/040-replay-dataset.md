## 파이프라인
```
.rep ─► uranium-replay::parse (헤더·플레이어·종족·맵·명령 스트림)
     ─► 필터 (1v1, 테란 포함, APM≥80, 길이≥5분, 중도 이탈 제외(= 길이 5분 미만 제외, 2026-10-16 사용자 확인; `dagger`는 길이 제외 없음, 041-R22), 맵 각 축 ≤128 타일(030-R6), 맵 해시 집계)
     ─► (SC:R 포맷이면) 1.16.1 명령 형식으로 변환 (040-R10)
     ─► OpenBW 재생 (011 재생 모드, 테란 시점 RawFrame + PrivilegedSummary)
     ─► 명령 정렬: 게임 시작 관측을 첫 스텝으로 두고(040-R18), 프레임 f의 사람 명령(select+order) → 의미 단위 액션(031·034 역변환), delay = 다음 액션까지 프레임, 32 초과 구간은 NoOp(031-R11)
     ─► 무효 레이블 비율 검사: 시점의 무효 레이블(BC 레이블 검사와 같은 함수) ≥ 20%면 `filtered` (040-R19)
     ─► shard 저장 (판단 시점의 RawFrame + PrivilegedSummary + 레이블, zstd 압축, 게임 단위. 로컬에 먼저 쓰고 공용 드라이브로 복사·검증, 040-R17)
학습 시: shard 로드 ─► feature·마스크 추출(030, 034) ─► 대칭 증강(030-R4) ─► BC (041)
```

```

  header: schema_version, feature_version, action_version, labeler_version   // labeler_version: schema 6부터
```

- `game_info.players`는 시점 플레이어와 실제 상대(리플레이의 다른 활동 플레이어) 두 명만 id 순으로 담고, `privileged`·`result`도 그 상대 기준이다(011-R10). 헤더에 빈 칸·활동 없는 칸이 있는 게임에서 상대가 실행마다 달라지던 문제(적 종족 feature·privileged·승자)를 고쳤다. schema 4 (2026-10-17, 위임 결정).
- schema 5 (2026-10-19, 전체 재build G-D1): `result_source`(040-R8 승패 판정 근거: `bridge`·`leave`·`recorded`·`none`)를 더하고, 스팸 병합 제거(040-R4)·게임 시작 관측 첫 스텝(040-R18) 등 레이블 변경을 반영해 전부 다시 만든다. 이전 schema shard는 쓰지 않는다.
- schema 6 (2026-10-19 사용자 결정, 액션 감사 F7·F12): header에 `labeler_version`을 더한다. 레이블러 버전 2는 R3(선택 전체 저장)·R11(`unknown` 레이블, `Unload_Unit`, order 매핑 보완)을 반영한 것이고 action 스키마 2(034-R2)로 만든다. **schema 5 shard도 계속 읽고 레이블러 버전 1로 본다**(header 외 레이아웃은 같다). schema 4 이하는 읽지 않는다.
- **혼합 데이터셋(2026-10-19 사용자 결정)**: G-D1 전체 재build는 진행 중에 part 경계에서 멈추고, 이미 끝났거나 진행 중이던 part는 레이블러 버전 1(schema 5, action 스키마 1)로 남고 남은 part는 버전 2(schema 6)로 만든다. 다시 만들지 않는다. 두 버전의 차이와 로더 처리:
  | 항목 | 버전 1 | 버전 2 | 로더·검사(`host_label_check`) |
  |---|---|---|---|
  | `selected` | `max_select`로 잘린 앞쪽 유닛 | 선택 전체(≤ 12) | 자격 필터 → 자기 대상 제외 → `max_select`로 자름. 버전 1은 결과가 이전과 같다(첫 유닛이 자격 없으면 무효로 남음, 마인 레이블의 약 8.6%) |
  | 미분류 명령 | 레이블 없음, 그 시간은 `NoOp` | `unknown` 레이블(가중치 0) | `unknown`은 NoOp으로 기억에 기록, R19·040-AC7 집계에서 제외 |
  | 단일 하차 0x29 | 미분류(`NoOp` 시간) | `Unload_Unit` | 버전 1에는 이 액션 레이블이 없다 |
  | Yamato(114)·TowerAttack(19) | 미분류 | `Yamato_Unit`·`Attack_Unit` | – |
  버전 1 시점의 위 차이는 알려진 손실로 받아들인다(합쳐 명령의 0.3% 안팎, 액션 감사 §7). records(`build` 기록)는 `labeler_version` 필드를 가지며 없으면 1이다. `dataset-stats`는 레이블러 버전별 시점·스텝·커버리지(`unknown` 포함)를, `shard-stats`는 버전별 shard·게임·스텝·`unknown`·`Unload_Unit`·`max_select` 초과 선택 레이블 수를 낸다.

## Acceptance Criteria
- 040-AC1: 파서가 샘플 1,000개 리플레이를 오류 없이 파싱하고, 결과가 기존 공개 파서의 명령 수·APM과 일치한다.
- 040-AC2: 디싱크 폐기율을 리포트한다(목표 < 10%). 폐기율은 재생한 시점 기준(`desync` ÷ (`written` + `desync`), 040-R16과 같은 단위)이고, 전체·`src`별·맵 패밀리별로 적는다.
- 040-AC3: 액션 역변환 커버리지 ≥ 95%(031-AC3).
- 040-AC4: 데이터셋 통계 리포트를 생성한다. 맵별 TvT/TvP/TvZ 게임 수와 시점 수(040-R6 집계 단위)가 포함되어야 한다.
- 040-AC5: SC:R 리플레이 샘플 100개를 변환·재생해 디싱크 비율을 리포트한다. 비율이 높아서(> 30%) 대상 맵 데이터가 부족하면 사용자에게 보고하고 대응을 확인받는다.
- 040-AC6: (조건부, 041-R9 스트리밍 경로를 구현할 때) 저장 데이터에서 생성한 feature와 재생 스트리밍으로 생성한 feature가 같은 리플레이에서 비트 단위로 일치한다.
- 040-AC7: (040-R19) 무효 레이블 비율이 20% 미만인 합성 시점은 저장하고 20% 이상(경계 20% 포함)인 시점은 `filtered`로 기록한다. build의 무효 레이블 수는 같은 게임에서 BC 로더(가중치 0 스텝 중 `unknown` 레이블(R11)을 뺀 수, 대칭·z 설정 무관)와 `label-check`의 사유별 수와 같다. `dataset-stats`는 필터 사유별 기록 수에 이 사유를 따로 센다.
- 040-AC8 (2026-11-05, 040-R21): 단위 테스트 — 절단 없음이면 모든 스텝, `--until-frame 11520`이면 11,520 이하(경계 포함)만 남는다. 시간 상한(2026-11-06): 리플레이 길이가 상한 이상(경계 포함)이면 ③ 신호와 승패(브리지 승자·퇴장)가 없어지고(판정 불가 0), 상한보다 짧은 판이나 옵션 없음이면 그대로다.

- 040-AC9 (2026-11-09, 사용자 확인 2026-11-09, 040-R22): 단위 테스트 — schema 7 shard에 `memory_action`이 있는 스텝과 없는 스텝이 왕복되고, schema 6·5 shard를 읽으면 모든 스텝이 `None`이며 나머지 내용이 이전 리더와 같다. `--src dagger` 이외 출처와 모델 결정 기록이 없거나 맞지 않는 판은 모든 스텝에 `None`만 쓴다(판 안에서 섞이지 않음).

## Risks & Open Questions
- **운영형 반례 교사 판 (2026-11-09 개정, 사용자 확인 2026-11-09, 040-R23)**:
